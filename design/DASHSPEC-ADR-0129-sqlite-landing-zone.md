# DASHSPEC-ADR-0129: SQLite landing zone

## Context

Источники DashSpec сегодня — SQL Server, Postgres, Xlsx-файл. Файловый мир
(csv/xlsx/json) входит в модель неровно: Xlsx живёт отдельным kind'ом,
csv — никак. При этом весь compile- и read-пайплайн уже db-first: карточки
читают таблицы/вьюхи, композитные источники компонуются server-side
(ADR-0126 §1), managed views публикуют детерминированный DDL (ADR-0125).

SQLite умеет жрать файлы разных форматов и живёт одним файлом. Это даёт
возможность не строить мосты «движок ↔ формат», а **нормализовать вход**:
любой файл превращается в таблицу в локальной файл-БД ещё на сборке отчёта.

## Decision

### 1. Landing-файл — build-артефакт, не источник

Новая команда **`dsc ingest <файл…> --into <report>.sqlite`**: csv/xlsx/json
конвертируются в таблицы SQLite-файла силами самого приложения. Файл-БД
лежит в проекте рядом со спекой — такой же обычный артефакт сборки, как
`DashSpec.TypedRows.dll` (ADR-0124) и `views/*.sql` (ADR-0125). Источник
`.ds` объявляет `from table <name>` / provider `sqlite` — компилятор не
различает, чем является таблица: файлом, сервером или landing-зоной.

### 2. Запись — только на сборке; просмотр — только чтение

Ingest выполняет **один** писатель на build-шаге. При просмотре отчёта
записи в БД **нет**: соединение открывается `Mode=ReadOnly`. Проблема
конкурентной записи отсутствует как класс — сколько бы зрителей ни смотрело
отчёт. Свежесть данных = пересборка файла: билд пишёт в новый файл и
подменяет его атомарно (rename), читатели продолжают видеть цельный
предыдущий файл до подмены.

### 3. Коннектор — обычный динамический плагин

SQLite-коннектор грузится как SqlServer/Postgres (папка `connectors/`).
Парсеры форматов (csv/xlsx/json) — тело ingest-команды коннектора. Типы
колонок маппятся в собственную динамику SQLite; **контрактом схемы остаётся
row type из `.ds`** — его уже проверяет compile (RowTypeAnalyzer), расхождение
landing-таблицы со спекой ловится при компиляции, а не на зрителе.

### 4. Диалект sqlite в эмиттере

`dsc build views --dialect sqlite` — `CREATE VIEW` без параметров (iTVF в
SQLite нет): параметризованные цепочки остаются на плоских VIEW, фильтры
едут outer WHERE (predicate pushdown) — для landing-файла это штатный путь,
не деградация. Composite SQL (ADR-0126 §1) работает как есть: композит
компонуется внутри одной БД, как и раньше.

## Consequences

+ Файловые источники входят через существующую db-first модель: коннектор +
  provider + row type — ноль новых концепций в языке.
+ Ноль инфраструктуры: отчёт на csv/xlsx поднимается без сервера БД —
  существенно и для демо, и для онбординга новых пользователей.
+ Конкурентность бесплатно: read-only зрители не блокируются и не блокируют.
− Данные верны на момент сборки: живых запросов к файлу нет (для
  операционных дашбордов файловых источников это и не случай).
− Парсеры форматов — поверхность коннектора: каждый новый формат = код
  парсинга и маппинга типов.

## Plan

1. SQLite-коннектор: read-only провайдер (query + provider infer), регистрация
   в динамической загрузке.
2. `dsc ingest`: csv/xlsx → таблицы landing-файла; атомарная подмена файла;
   `--dialect` для типов колонок.
3. Диалект sqlite в `ManagedViews`-эмиттере (flat VIEW only).
4. Демо: ai-landscape или demo-корпус на csv + xlsx-источниках end-to-end.
