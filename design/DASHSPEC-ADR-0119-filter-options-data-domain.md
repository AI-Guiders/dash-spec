# DASHSPEC-ADR-0119: Опции field-фильтра — из скоупа экземпляра (домен данных владельца)

> **Superseded by [ADR-0120](DASHSPEC-ADR-0120-filters-as-flow-nodes.md)** —
> скоуп-модель здесь сохранена как ступень; её носителем стал граф потоков
> (узлы вместо осей реестра). Кейс-трасса ниже остаётся актуальной как
> мотивация ADR-0120. Примеры обезличены: закрытый контент-репо, генерик-домен
> `demo.v_events_detail` (как в ADR-0037).

## Context

Кейс, доведённый до боли живым экраном (внутренний отчёт из закрытого
контент-репо, 2026-11-06): выбор значения в field-фильтре схлопывает матрицу.
Пользователь выбирает значение из списка — а на диаграмме после этого пусто:
выбранное значение в периоде карточки не встречалось вовсе.

Сегодня (факты, трасса по коду):

- **Опции строятся из словаря таблицы, без скоупа**: `ReportFieldOptionsLoader`
  (ADR-0099) на бутстрапе выполняет `QueryCompiler.BuildDistinctFieldSql(filter)`
  → `SELECT DISTINCT event_type FROM demo.v_events_detail` — **одно безусловное
  утверждение**. Ни периода, ни связи с запросом карточки.
- **Декларация фильтра**: таблица-квалифицированная колонка
  `demo.v_events_detail.event_type` — ровно то, что ADR-0099 требует для
  загрузки опций (`CanLoadDistinctFieldOptions`).
- **Данные матрицы скоупнуты**: карточка выполняет свой запрос с локальным
  периодом (per-card: у одной карточки — неделя, у соседней — день) и
  группировкой; ряды матрицы = значения, активные **в периоде**.
- **Расхождение списков** наблюдаемо: в фильтре ~40 значений, на матрице в
  выбранном дне — 25. Разница = мёртвые в периоде значения; их выбор даёт
  0 рядов.
- **Значения фильтра — per-card**: карточки секции хранят выбор независимо
  (наблюдаемо: значение выбрано на одной карточке, соседняя показывает всё),
  но список опций один — `_fieldOptions` грузится один раз на документ
  (`ReportSession.GetFieldOptions`), ключ кэша = `{runtime}:{connector}:{sql}`.

Следствие для пользователя: список обещает значения, которых в периоде нет;
выбор «пустого» — единственный путь к схлопыванию, и он лежит на самом виду.

## Диагноз уровня модели

Проблема не в loader'е как таковом, а в дыре в модели фильтров. ADR-0037
определяет четыре оси — bind, show, **видимость** (`toolbar` / `page toolbar` /
`card filters`), layout — но видимость отвечает только на вопрос «где нарисовать
виджет». Объявление, состояние и **домен кандидатов** — одни на весь документ:
один id = одна запись реестра = один список опций на бутстрапе.

При этом card-scope уже работает де-факто через адресацию
(`event_type -> [toolbar] chrome.card.X`): у каждой карточки свой экземпляр
тулбара и своё значение. Модель просто не признаёт этого словами.

## Decision (draft, superseded — носителем стала граф-модель ADR-0120)

**Скоупы как области видимости у языков программирования.** Ось «видимость» из
ADR-0037 поднимается до оси **«скоуп»**: видимость становится следствием скоупа.

```
report-scope:  filter event_type (toolbar отчёта) → один экземпляр: одно состояние, один список опций
card-scope:    filter event_type (filters в card) → карточка живёт со СВОИМ экземпляром
```

- Одинаковые id в разных скоупах легальны — как одноимённые переменные разных
  областей. Разрешение однозначно по месту: иерархия фиксированная
  (report → card), теневого поиска «ближайшего объявления» не возникает.
- Синтаксис, по всей видимости, **не меняется**: `card filters event_type` уже
  говорит «локальный» — меняется его *значение*. IR уже знает `LocalFilters`;
  дописывается только резолюция домена в loader'е.

### Резолюция опций по скоупу экземпляра

Загрузчик опций спрашивает не «какая колонка?», а **«чей это экземпляр?»**:

| Скоуп экземпляра | Домен опций | SQL |
|---|---|---|
| **card-scope** | домен своей карточки: её диаграмма, её период, её таблица | `SELECT DISTINCT event_type FROM demo.v_events_detail WHERE event_date = @card_date` — тот же WHERE, что у данных матрицы |
| **report-scope** | union доменов карточек, на которые фильтр bind'ится | union per-card distinct'ов |
| **висит без bind** | деградация к словарю (сегодняшнее поведение) | `SELECT DISTINCT ...` без скоупа, как сейчас |

Card-scope — главный выигрыш: список **ровно совпадает с матрицей**, потому что
строится из того же периода и тем же WHERE, что и данные карточки. Ни
union-хвостов, ни расхождений.

### Жизненный цикл

- Опции грузятся **лениво**, при первом открытии фильтра карточки (на бутстрапе
  периода ещё нет); кэш-ключ = `{card}:{connector}:{sql}:{from}:{to}`.
- Смена периода карточки инвалидирует её список (тот же флоу, что и данные).
- Словарный путь ADR-0099 (`LoadFieldOptionsAsync` на бутстрапе) остаётся для
  фильтров без bind — словарное поведение не умирает.

## Alternatives considered

- **`distinct_scope = event_date` в декларации фильтра** (первый draft этого
  ADR): фильтр декларирует date-колонку, distinct строится с её скоупом.
  Отклонено: дублирует связь, которую data-flow уже знает (`event_type ->
  [toolbar] chrome.card.X`), а семантика «в периоде таблицы» честнее
  выглядящего, но слабее — не гарантирует совпадения с конкретной диаграммой
  (у той могут быть свои `top`/группировки).
- **Опции из результата запроса карточки** (distinct по готовым строкам): без
  SQL, всегда совпадает с матрицей — но `series max` сворачивает хвост в
  «Другие», и в результате отдельных значений хвоста нет. Может пригодиться
  как **второй уровень** поверх card-scope, но не как база.
- **Словарные опции + дизейбл отсутствующих**: тот же distinct с датой, только
  ради серого флажка. Пользователь видит мусор. Отклонено как полумера.
- **Union для card-scope**: если фильтр течёт в несколько карточек, показывать
  объединение. Отклонено именно для card-scope: у карточки свой экземпляр — его
  домен должен быть её собственным, иначе список снова перестаёт совпадать с
  её матрицей. Union — семантика report-scope.

## Consequences

- `+` список фильтра совпадает с доменом данных владельца: ловушка «выбрал — а
  там пусто» исчезает на уровне модели, не UX-костылём.
- `+` card-scope получает точную семантику задним числом — то, что уже работает
  де-факто через адресацию тулбара, становится словами модели.
- `+` парсер и IR почти не трогаются: дописывается резолюция домена в loader'е.
- `−` опции становятся ленивыми и per-instance: сложнее кэш, больше запросов
  (по одному на открытие фильтра/смену даты; view узкая, distinct дёшев).
- `−` ADR-0037: ось «видимость» получает вторую роль (скоуп) — документацию
  четырёх осей надо переписать на «скоуп (→ видимость)».
