# DASHSPEC-ADR-0119: Опции field-фильтра — из домена данных карточки, не из словаря таблицы

## Context

Кейс, доведённый до боли живым экраном (Обзор LUS, 2026-11-06): выбор продукта в
фильтре «Продукты» схлопывает матрицу. Пользователь выбирает продукт из списка —
а на диаграмме после этого пусто: выбранный продукт в периоде карточки не
встречался вовсе.

Сегодня (факты, трасса по коду):

- **Опции строятся из словаря таблицы, без скоупа**: `ReportFieldOptionsLoader`
  (ADR-0099) на бутстрапе выполняет `QueryCompiler.BuildDistinctFieldSql(filter)`
  → `SELECT DISTINCT app_name FROM demo.v_daily_active_events` — **одно безусловное
  утверждение**. Ни периода, ни связи с запросом карточки.
- **Декларация фильтра** (`demo-dev-overview.ds:42`): таблица-квалифицированная
  колонка `demo.v_daily_active_events.app_name` — ровно то, что ADR-0099 требует
  для загрузки опций (`CanLoadDistinctFieldOptions`).
- **Данные матрицы скоупнуты**: карточка выполняет свой запрос с локальным
  периодом (`usage_date` per-card: у «Пика» — неделя, у «Активности за день» —
  день) и группировкой; ряды матрицы = продукты, активные **в периоде**.
- **Расхождение списков** наблюдаемо: в фильтре ~40 продуктов
  (AppThree, AppTwo, AppOne 22025R1…), на матрице «Активности» в выбранном
  дне — 25. Разница = мёртвые в периоде продукты; их выбор даёт 0 рядов.
- **Значения фильтра — per-card, опции — документные**: карточки секции хранят
  выбор независимо (наблюдаемо: AppOne выбран на «Активности», «Пик» показывает
  всё), но список опций один — `_fieldOptions` грузится один раз на документ
  (`ReportSession.GetFieldOptions`), ключ кэша = `{runtime}:{connector}:{sql}`.

Следствие для пользователя: список обещает продукты, которых в периоде нет;
выбор «пустого» — единственный путь к схлопыванию, и он лежит на самом виду.

## Decision

**Рекомендация (draft, на обсуждение): опции из домена данных периода** —
distinct с датаскоупом карточки. Синтаксис в спеке, планировка и открытые
вопросы — ниже; ничего из этого не имплементировано.

### 1. Декларация получает скоуп: «опции фильтра = значения поля в периоде»

Фильтр связывается с date-колонкой данных (не с card-параметром напрямую):

```
filters
  | app_name | field | demo.v_daily_active_events.app_name | Продукты | combobox | app_name | distinct_scope = usage_date |
end filters
```

`distinct_scope` называет колонку периода **той же таблицы**, поэтому distinct
строится как:

```sql
SELECT DISTINCT app_name
FROM demo.v_daily_active_events
WHERE usage_date >= @from AND usage_date < @to
```

Семантика для пользователя: «в списке — продукты, которые вообще были активны
в выбранном периоде». Мёртвые продукты исчезают из списка автоматически.

### 2. Опции становятся per-card, грузятся лениво, кэш по периоду

- Раз дат разных на карточку — список опций у каждой карточки свой (то же
  слово фильтра, разные домены). Это не ломает per-card значения: у каждой
  карточки свой список кандидатов и свой выбор.
- Грузить не на бутстрапе (там ещё нет периода), а при первом открытии фильтра
  карточки; кэш-ключ = `{connector}:{sql}:{from}:{to}`; перезагрузка при смене
  даты карточки.
- `LoadFieldOptionsAsync` (бутстрап-путь ADR-0099) остаётся для фильтров без
  `distinct_scope` — словарное поведение не умирает, скоуп — опция декларации.

### 3. Период меняется — опции перечитываются

Смена даты карточки инвалидирует её список опций (тот же флоу, что и данные).
Дебаунс/ленивость — как у данных: список нужен только при открытии фильтра.

## Alternatives considered

- **Опции из результата запроса** (distinct по готовым строкам карточки): без
  SQL, всегда совпадает с матрицей. Отклонено пока: `series max = 12` сворачивает
  хвост в «Другие» — в результате отдельных продуктов хвоста нет, и список снова
  расходится с матрицей, только наоборот (в списке есть, в матрице свёрнут).
- **Словарные опции + дизейбл отсутствующих**: сохраняет один список, но требует
  «запрос присутствия» — тот же distinct с датой, только ради флажка. Пользователь
  видит мусор (пусть и серый). Отклонено как полумера.

## Open questions (на обсуждение завтра)

1. **Синтаксис**: `distinct_scope = usage_date` в хвосте строки фильтра vs
   именованный блок `options` vs связь через data-flow граф (`app_name ->
   [app_name] heatmap` уже связывает фильтр с диаграммами — может, скоуп должен
   наследоваться от связи с диаграммой, а не декларироваться?).
2. **«Другие»**: показывать ли в списке сгруппированные продукты хвоста
   (`series max = 12`)? Если да — их выбор должен разворачивать группу?
3. **Пустой скоуп**: если в периоде нет ни одного продукта (дата без данных) —
   пустой список или деградация к словарю?
4. **Секции с разными датами**: подтвердить, что per-card списки — желаемая
   семантика (в Обзоре даты карточек уже разъехались — это легитимно?).
5. **ADR-0062**: выбранные значения, отсутствующие в новом скоупе (период
   сузился) — сбрасывать или хранить серыми?

## Consequences

- `+` список фильтра всегда совпадает с доменом данных периода: ловушка
  «выбрал — а там пусто» исчезает на уровне данных, не UX-костылём.
- `+` мёртвые продукты исчезают из списка — список короткий и честный.
- `−` опции становятся ленивыми и per-card: сложнее кэш, больше запросов
  (по одному на открытие фильтра/смену даты; view узкая, distinct дёшев).
- `−` синтаксис фильтра растёт на одно поле; ADR-0118 получает соседа —
  «домен кандидатов» из его контракта получает источник.
