# DASHSPEC-ADR-0111: Собранная слотовая плоскость — SSOT визуальной композиции

## Context

**Каноническая модель уже существует и развёрнута** — [ADR-0072] «Unified layout slot plane» (2026-10-01, миграции M1–M5 **done**): одна идея — «грид слотов, слот держит типизированный компонент»:

- `LayoutSlotDescriptor(Token, Placement, Scope, ContentKind)` — ячейка: токен, размещение (`PlacementDefinition { Row; Col; Span }`), scope (`HostTabBoard | HostPageToolbar | CardInterior | CardFilterChrome`), содержание (`Card | Nest | Group | Filter | PrimaryDiagram | SecondaryDiagram`);
- `LayoutSlotEngine.PlanCardInterior / PlanHostPageToolbar / PlanHostTabBoard / PlanHostTabBoardCards` — планировщики (математика одна, рекурсивная);
- `PlacementSlotGrid`/`PlacementSlot` (Presentation) + `ILayoutSlotRendererRegistry` — рендер диспетчится по `(Scope, ContentKind)`, не по Razor-веткам;
- ментальная модель автора — **две вложенные сетки** (host → card), те же правила слотов.

Чего нет — **собранной разом плоскости**: код планировщиков лежит в C# `Execution.Runtime`, но **вызывается из Surface по-рендерно** — `DashboardFiltersSection.razor:161` планирует тулбар прямо в Razor-компоненте при отрисовке; `DashboardPageController.cs:785/791` планирует доску вкладки на каждый запрос; интерьеры — `PlanCardInterior` через Viz-расширение (`CardInteriorSlotPlanExtensions`) при отрисовке карточки; плюс fallback-ряд тулбара L1297–1321 и `RecomputeToolbarPlacements`, per-render `DashboardLayoutHelper.ResolveInteriorPlacements`. Каждый вызов пересчитывает свой срез геометрии под свой контекст, целое нигде не собирается. Отсюда же эвристики хоста: «первая вкладка/страница» (`ResetActivePageForTab` L1420, дубль `TabLayoutCompactor` L40–43), скрытие nav по `Count > 1` (6 мест), label-эвристики, видимость тулбар-фильтров пересечением с картами (`ToolbarFilterVisibility` — то, что §4 ADR-0074 запрещает Host'у).

Оператор (2026-10-21, постановка): отделить структуру от рендера — **сборка слотов предварительная, хосту остаётся только отрисовать**. Форма уже принята каноном [ADR-0072]; этот ADR доводит её инвариант до конца: **одна собранная плоскость вместо повторных планирований на рендере**.

## Decision

### 1. Артефакт — `SlotPlane`: собранная плоскость; слот-модель — в F#-модельном слое, у своих сиблингов

Ни одного нового узла. Сначала — переезд чистых модельных записей домой: `LayoutSlotDescriptor`/`LayoutSlotScope`/`LayoutSlotContentKind` (чистые данные, ноль поведения; [ADR-0072] писала «DashSpec.Core.Layout») сегодня сидят в C# `Execution.Runtime`, тогда как их сиблинги `PlacementDefinition`/`LayoutDefinition` живут в F# `Modeling.Parse.Layout` — записи переезжают туда же, **рядом с `PlacementDefinition`** (механический переезд чистых записей, **не** порт: `LayoutSlotEngine` и планировщики остаются в C# `Execution.Runtime` и просто производят F#-записи — как уже всё потребляет F#-документ).

```fsharp
// Modeling.Parse/Layout — рядом с PlacementDefinition/LayoutDefinition (LayoutTypes.fs)

// Слот собранной плоскости: жилец — БУКВАЛЬНО узел графа документа ([ADR-0091]:
// WiringNode { Id; Kind; Scope }), кладётся как есть; никаких DU-копий объектов —
// сущности остаются в документе, рендер получает их как сегодня.

[<CLIMutable>]
type Slot =
    { Node: WiringNode                     // жилец: узел графа документа, как есть
      Placement: PlacementDefinition      // row/col/span — существующая запись
      Scope: LayoutSlotScope               // существующий (HostTabBoard | HostPageToolbar | CardInterior | CardFilterChrome)
      Provenance: PlacementProvenance }     // объявлено | умолчание записано ([ADR-0109])

[<CLIMutable>]
type BoardRoute =
    { TabId: string
      PageId: string option }                 // None — вкладка без страниц

[<CLIMutable>]
type SlotPlane =
    { Boards: IReadOnlyDictionary<BoardRoute, IReadOnlyList<Slot>>        // эффективная доска на маршрут
      PageToolbars: IReadOnlyDictionary<string, IReadOnlyList<Slot>>      // ключ — PageId
      CardInteriors: IReadOnlyDictionary<string, IReadOnlyList<Slot>>   // ключ — CardId
      CardFilterChrome: IReadOnlyDictionary<string, IReadOnlyList<Slot>> // ключ — CardId
      InitialRoute: VisualRoute }                                           // записанное умолчание

[<CLIMutable>]
type VisualRoute =
    { EntryId: string
      TabId: string
      PageId: string }

[<RequireQualifiedAccess>]
type PlacementProvenance =
    | Declared            // автор объявил ячейку в спеке
    | RecordedDefault     // сборка подставила умолчание и ЗАПИСАЛА его ([ADR-0109])
```

- **Доска — на маршрут (вкладка, страница)**: страницы владеют досками (page-board перекрывает tab-board) и фильтруют карточки (`ResolveContext`: карточки по `PageId`) — плоскость предвычисляет **эффективную доску на каждый маршрут** (все вкладки × их страницы + безстраничные вкладки), хост — один lookup по активному маршруту, без веток.
- **Жилец — узел графа документа, по соответствию**: скомпилированная штука ↔ её визуальная запись — та же связь, по которой к документу добавляли вещи при компиляции (`ResolvedModuleDiagrams`, wiring-граф [ADR-0091]), только теперь визуальный слой. Узел кладётся в слот как есть — ничего не «резолвится»: всё уже отпарсено и скомпилировано. Ни одной строки-идентичности, ни одной копии объекта: сущности — у документа, их рендер получает как сегодня; плоскость — **структура**, а не контейнер сущностей.
- **Диспетчеризация рендера** — по `(Scope, Node.Kind)` (кейс из узла): реестры [ADR-0072] адаптируются при переключении потребителей (P1).
- **Вложенность — существующая**: две сетки (host → card) + nest/group; слот карточки на доске вкладки и `CardInteriors[cardId]` — ключом `CardId`; placement — метка на слоте, как `Grid.Row`.
- **Умолчания — `Provenance` на слоте** (объявлено | записано), не множество стрингов.
- **Открытое ребро (честно)**: у графа документа нет узлов `Nest`/`Group` — это структурные контейнеры; их слот-рамки решаются при P0 по живому инстансу (либо структурные узлы входят в граф, либо рамка группы держит ссылку на свою декларацию) — не предрешается здесь.

### 2. Сборка — соответствие, одна точка, один раз на ревизию; математика потребляется как есть

Ничего не «резолвится» — всё уже отпарсено и скомпилировано. Сборка — **соответствие: скомпилированная штука ↔ её визуальная запись** — та же связь, по которой к документу добавляли вещи при компиляции (`ResolvedModuleDiagrams`, wiring-граф [ADR-0091]), только теперь визуальный слой. Соответствие сегодня уже есть — оно живёт на рендере (`ResolveLayoutCardRef` в контроллере, по-рендерные вызовы планировщиков) и переезжает **по моменту раньше**, не переделываясь.

`SlotPlaneBuilder` — в `Execution.Runtime`, **рядом с `LayoutSlotEngine`, которого он вызывает**: (`DashboardDocument` + `CatalogDocument`) → `SlotPlane`. Все существующие планировщики (`PlanHostTabBoard*`, `PlanHostPageToolbar`, `PlanCardInterior`, компакторы/резолверы) **остаются на своих местах — их вывод ложится в плоскость**. Никакого порта: переписывание работающей математики без второго инстанса — churn ([ADR-0108]).

Точка сборки — **bootstrap загрузки отчёта** (`ReportSpecBootstrap`): один вызов на загрузку/ревизию документа, артефакт едет в bootstrap-результате рядом с документом и wiring-графом ([ADR-0091]). Параллель имён: `DocumentWiringGraphBuilder` (данные) + `SlotPlaneBuilder` (структура).

Плоскость **маршруто-независима**: все вкладки, страницы, интерьеры и хромы сразу. Никакой «нарезки по маршруту»: смена вкладки в хосте — выбор среза, не пересборка.

**Оболочка — тоже грид** (оператор, 2026-10-21): никакого понятия «зоны» — оболочка это ещё один контейнер в плоскости, сайдбар — просто слот `nav`, занимающий первую колонку с нужным спаном. Существующие гриды, существующие слоты, существующие спаны — ноль новой грамматики. [ADR-0110] сворачивается к этому принципу.

**Оболочка — из host-модуля, не из плоскости дашборда** (оператор, 2026-10-21, ревизия §2): раскладка оболочки живёт в ds — scope-host борда host-модуля (`import layouts from <ns>`, грамматика [ADR-0026]/[ADR-0054] уже была) — и хост рендерит свой ds **сначала**: слоты хрома + слот `content`, размещение как записано. Слоты хрома не входят в wiring-граф дашборда (нет проводки — нечего графить), `SlotPlane.Shell` и синтез дефолта в коде умерли. Дефолт при отсутствии борды — **EmbeddedResource `host.ds`** (обычный ds-файл в сборке хоста: `[ brand . nav ] / [ content ]`), не синтез в коде. Слот `content`, не объявленный в борде, неявно занимает следующую строку — записанное умолчание. Неизвестный слот в борде — громкая ошибка (соответствие, не намёк). Резолвер один — `ShellBoardSlotResolver` (Runtime, соответствие). Embedded-дефолт читает `HostShellBootstrap` (ресурс хоста, не второй резолвер).

**Модель клетки — star-sizing как в WPF Grid** (оператор, 2026-10-21, эксперимент принят): строка борды — массив клеток, борда — матрица (люди записывают текстом именно массивы и матрицы). Клетка — три состояния: `имя` — Auto (по контенту); `имя:вес` — N* (доля свободного места, [ADR-0061] `ref:weight`, вес — положительное целое, дефолт 1); `.` — пустая N* (резинка: свободное место — растяжка, `.:вес` — пропорция между резинками). **Запись одна для всех борд, дефолт читает потребитель**: карточные ряды — `LayoutBoardRowPlacer.PlaceRow` (вес = доля ряда, одна клетка — вся ширина, последняя — остаток); хром-ряды — `ShellBoardSlotResolver` (имя без веса = Auto, кнопка — своей ширины; `content` — жадный, занимает клетку целиком; ряд из одних резинок — громко). Повторы имён для спанов — **отвергнуты** (оператор): спан по строке — числом (`content:3` — как `3*`), не повторением. Сайдбар — строкой матрицы (строка тела тянется вниз: рендер — колонка flex, тело — `flex:1`), rowspan не нужен.

**Сетка рисуется пустышками `[]`** (оператор, 2026-10-22): `layout grid` — рисунок из `[]`-клеток (токен-целое в лексере, `[` сразу `]`): сколько рядов нарисовано — столько строк, сколько `[]` в ряду — столько колонок (самый широкий ряд выигрывает; jagged-формы вальны). Пустышка — одна сущность везде: и в рисунке сетки, и пустая клетка в борде (точка-резинка умерла, `[]` вместо неё). **Числа мертвы и громки при встрече**: `columns = N` и `gap = N` — блок сетки — чистый рисунок, никаких свойств. Дефолт сетки живёт в ds, не в коде: хост регистрирует рисунок из embedded `host.ds` (тот же файл, что несёт shell-борду) как умолчание для документов без своей сетки (`GridDefaultBridge`, `LayoutParser.defaultGrid`); нигде нет — громко. В юнит-тестах тот же стенд регистрируется явно (ModuleInitializer где C#, `do ensure ()` где F# — F# ModuleInitializer не умеет, FS0202). Layout-модули несут опциональный одиночный `grid`-блок перед бордой (`LayoutBoardDefinition.GridColumns`, 0 = не нарисован). **Зазоры похоронены** (оператор, 2026-10-22): `GapPx` мёртв после fluid-фикса — зазор — визуальный слой (CSS `clamp`, «дышит»), не спека; `LayoutDefinition` несёт только `Columns`.

**Громкая семантика** ([ADR-0109]): соответствие не сложилось (ссылка на несуществующую штуку) — ошибка сборки; умолчания — записаны (`Provenance: RecordedDefault` на слоте).

### 3. Сессия — оверлей, не мутация

Fold (`fold = independent` уже в спеках), занятость, активная `(tab, page)`, выбор — состояние сессии в хосте, **наложенное** поверх иммутабельной плоскости при рендере. Плоскость не мутирует от взаимодействия; «активный выбор, busy — это сессия, а не композер» (§4 ADR-0074).

### 4. Рендер — читает уже собранную модель и размещает

Рендер уже диспетчит по `(Scope, ContentKind)` ([ADR-0072] M5) — меняется только **вход**: сегодня Surface зовёт планировщиков при каждой отрисовке, после ADR рендер **читает уже собранную модель и размещает** — срез за срезом, ноль вычислений. Код планировщиков не переезжает — переезжает вызов. Потребители переключаются **по одному месту вызова**, видимое поведение сохранено на каждом шаге:

| Вызов/эвристика сегодня | Становится |
|-------------------|------------|
| `DashboardFiltersSection.razor:161` → `PlanHostPageToolbar` на отрисовке | Чтение среза `PageToolbars[pageId]` |
| `DashboardPageController.cs:785/791` → `PlanHostTabBoard*` на каждый запрос | Чтение среза `TabBoards[tabId]` |
| Per-render `PlanCardInterior` (Viz-расширение) / `ResolveInteriorPlacements` | Чтение среза `CardInteriors[cardId]` |
| «Первая вкладка» (`DashboardPageController` L1180) | `InitialRoute.TabId` — записанное умолчание |
| «Первая страница» (`ResetActivePageForTab` L1420, дубль `TabLayoutCompactor` L40–43) | `InitialRoute.PageId` — записанное умолчание |
| Скрытие nav при `Count > 1` (6 мест) | Рисуется объявленное; умолчание — записано |
| Label-эвристика `Tabs.Count > 1` (`DisplayResolution.ResolveTabLabel`) | Label в артефакте, Host читает готовое |
| `ToolbarFilterVisibility` (пересечение с картами) | Спек-объявленные слоты + флаг `Bound`; рендер рисует disabled, не прячет (§4 ADR-0074) |
| Fallback-ряд тулбара (L1297–1321) / `RecomputeToolbarPlacements` | Умолчание, записанное при сборке |

### 5. Языковая добавка (минимальная, по духу ADR-0109)

Catalog entry получает `page <pageId>` симметрично `tab <tabId>`: `InitialPageId: string option`. Сборка валидирует громко; fallback «первая запись» — заменяется записанным умолчанием.

### 6. Приёмка фундамента — визуальная

Плоскость считается готовой по срезу, когда тупая диспетчеризация этого среза даёт задуманный вид (conformance-цели — экраны образца «взрослого BI», HTML-образец Сергея), включая масштаб и вьюпорт-классы (§7). Фундамент не уезжает в абстракцию, потому что его проверяют глаза.

### 7. Адаптивность — варианты по классу вьюпорта: анализ доступного пространства на этапе планирования

Сегодня геометрия статична и слепа: `LayoutDefinition { Columns; GapPx }` → `--grid-gap:{GapPx}px` — фиксированные пиксели и фиксированное число колонок, ни одного `@media`/breakpoint/`minmax` по вьюпорту во всей вёрстке (проверено). Отсюда наблюдение оператора: при зуме контент растёт, зазор стоит — «пропадает»; на неудачных вьюпортах колонки не заполняются — «огромные». Анализа доступного пространства нет.

Решение — по формуле оператора «браузер один → всё предварительно посчитать перед собственно размещением»: **плоскость собирается вариантами по классу вьюпорта**. Та же математика планировщиков прогоняется раз на класс (`wide | mid | narrow` — стартовый набор по живым инстансам, [ADR-0108]): компакция, спаны и умолчания считаются под доступное место каждого класса. Браузер переключает вариант **медиа-запросом** — чистый CSS, ноль рантайм-вычислений. В CSS-проекции допустимы fluid-токены (`clamp()`, `fr`) внутри класса.

## Rejected

| Идея | Почему |
|------|--------|
| **Выдуманное параллельное дерево (`VisualNode`/`VGrid`/`VRow`/`VSlot`/`VCard`/`VisualChild`…)** (правки этого же дня, несколько итераций) | Каноническая модель уже есть и развёрнута — [ADR-0072] слотовая плоскость, M1–M5 done: дескрипторы, планировщики, реестры, «две вложенные сетки». Изобретать поверх неё второе дерево — параллельная истина; нужно было **прочитать канон до проектирования**. Остальное этого дня — подвиды той же ошибки: scope-строки, листья `of string`, узлы-«строки доски», порты математики, новые проекты |
| **C#-артефакт, привязанный к месту посадки слот-типов** (правка этого же дня) | Модель — на F# у сиблингов: чистые записи (`LayoutSlotDescriptor`/`Scope`/`ContentKind`) переезжают в `Modeling.Parse/Layout` рядом с `PlacementDefinition`; переезд механический, не порт — `LayoutSlotEngine` остаётся в C# `Execution.Runtime` и производит F#-записи; артефакт `SlotPlane` — с ними в модельном слое |
| `VisualModel` + `VisualCompositor` (`be18e71`/`4e490a4`) | Композитор с «нарезкой по маршруту» — сессия, не слой; артефакт маршруто-независим |
| Перенос merge таб-модулей в рантайм | Merge — конвейер компиляции ([ADR-0097]) |
| Скрывать тулбар-фильтры эвристикой пересечения | Нарушает §4 ADR-0074; честный путь — слоты + `Bound` + disabled-состояние |
| Новый проект для P0 | Артефакт — `Execution.Runtime`, рядом с `LayoutSlotEngine` |

| **P1** | Потребители Surface переключаются по одному месту вызова (§4): per-render резолвы → чтение срезов; fallback-ряды → `RecordedDefaults`; каждый шаг — видимое поведение сохранено |
| **P2** | Оболочка = ещё один грид (оператор: «зоны — лишнее»): сайдбар = слот `nav` в первой колонке, host-доска в плоскости; `page <id>` в каталоге |
| **P4** | Адаптивные варианты (§7): классы вьюпорта в плоскости, медиа-запросы в CSS-проекции, fluid-токены; conformance по масштабу |
| ~~P3 Studio~~ | Отложено оператором — всё делается ради визуала, Studio потом |

## Consequences

- Одна собранная плоскость = один источник для Blazor, плагинов, Studio и headless-экспорта; воспроизводимость из артефакта.
- Ничего нового в модели слотов: дескрипторы/планировщики/реестры [ADR-0072] — как были; новое — точка сборки, артефакт-контейнер и записанные умолчания.
- Surface перестаёт быть «вторым автором»: гейты и fallback-пересчёты умирают по одному.
- Визуальная итерация — правка декларации + дамп плоскости: собрал, посмотрел композицию целиком.
- Два SSOT — данные (wiring-граф, [ADR-0091]) и структура (SlotPlane) — собираются рядом в одном bootstrap-результате.
- [ADR-0110] обновлена на термин `SlotPlane`.
