# DASHSPEC-ADR-0124: Row types становятся CLR-типами через Source Generators

## Context

Спека декларирует типы строк (`type LufEventRow { … }`), но компилятор DashSpec
хранит их как данные (`RowTypeDef` в каталоге) — CLR-типа не существует. По дороге
к рендеру доменный объект теряется: reader материализует плоские `DashValue[]`,
и рендер получает безымянный массив. Wire-контракт ADR-0087 (значение + схема
рядом) это узаконивал — ценой того, что нативные механизмы гридов
(LINQ-выражения по свойствам `TItem`: группировка, сортировка, фильтры) не
работают: у массива нет членов.

Группировка таблиц (ADR-0123) упёрлась в это же: Radzen `AllowGrouping` требует
POCO, и нам пришлось собирать группы руками. Вариант «порождать CLR-типы в
рантайме» (Emit) отвергнут — рефлексия/генерация на горячем пути. Roslyn
Source Generators дают то же самое без рантайм-генерации: типы рождаются на
компиляции, в IL.

## Decision

**Row types из спек компилируются в CLR-типы Source Generator'ом; рантайм
связывает каталог с ними по имени; рендер получает честный `TItem`.**

1. **`DashSpec.SourceGenerator`** (пакет движка): парсит types-юниты из
   `AdditionalFiles` (`**/*.ds`) и эмитит `sealed class` с типизированными
   свойствами (`date` → `DateOnly?`, `string` → `string?`, `int` → `int?`,
   `decimal` → `decimal?`, `datetime` → `DateTime?`, …) плюс конструктор из
   `DashValue[]` (значения через `ToClr()` + unbox).

2. **Сгенерированный реестр**: `RowTypeRegistry.MapFromName` —
   `имя → typeof(T)` и `имя → фабрика(DashValue[]) → object`; модульный
   инициализатор регистрирует все типы сборки.

3. **Типогенерирующая обвязка корпуса** — csproj рядом со спеками (не dsproj:
   Roslyn не видит наш формат):
   ```xml
   <Project Sdk="Microsoft.NET.Sdk">
     <ItemGroup>
       <PackageReference Include="DashSpec.SourceGenerator" Version="…" />
       <AdditionalFiles Include="**/*.ds" />
     </ItemGroup>
   </Project>
   ```
   Сборка корпуса порождает `TypedRows.dll`. `.dsproj` остаётся спечным
   проектом как есть; csproj — тонкая обвязка над теми же файлами.

4. **Рантайм-связка**: при материализации батча reader спрашивает реестр по
   `RowsType`; тип найден → строки материализуются как CLR-объекты, рендер
   получает `TItem` (generic-компонент через `MakeGenericType` +
   `DynamicComponent`). Не найден → текущий wire-путь (`DashValue[]`).

5. **Гибридный fallback**: спеки, загружаемые рантаймом (без сборки), живут на
   wire-пути — интерактивная группировка для них остаётся ручной (ADR-0123).
   Для SG-корпусов нативные механизмы гридов (группировка, сортировка,
   фильтры через их expression-слой) работают из коробки.

## Alternatives considered

- **Runtime-генерация типов (Emit)** — запрещена линией проекта; SG даёт то же
  без рантайм-механики. Отвергнуто.
- **Остаться на wire-массивах навсегда** — каждый нативный механизм гриды
  приходится reimplement'ить руками (группировка уже, сортировка/фильтры
  следующие). Отвергнуто как накопление ручного дубля.
- **Dictionary<string, object> строки** — не члены типа, LINQ-выражения
  не работают. Не вариант.

## Consequences

- `+` доменный объект по всей дороге: спека → CLR → рендер; имена и типы
  полей живут в одном месте (types-юнит спеки).
- `+` нативные группировка/сортировка/фильтры гридов работают для
  SG-корпусов без ручных реализаций.
- `+` ноль рефлексии на горячем пути: генерация — на компиляции; рантайм —
  один lookup по имени при связке.
- `−` корпусу нужна csproj-обвязка (одна, три строчки) и перекомпиляция при
  смене типов строк.
- `−` два пути рендера (typed/wire) до тех пор, пока wire-fallback жив.
