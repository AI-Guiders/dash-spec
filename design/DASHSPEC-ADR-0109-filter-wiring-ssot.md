# DASHSPEC-ADR-0109: SSOT проводки фильтров клика

## Статус

Принято (2026-10-21). Оператор указал на системность: два тихих провала в
подсистеме фильтров за одну сессию.

## Контекст

Фильтр клика (`set app_name=y` в `on click`) доходил до SQL через **две
независимые декларации**:

1. определение фильтра (filters);
2. привязка фильтра к слоту в data flow (`app_name -> [app_name] users`).

Обе проваливались **молча**:

- бинд на несуществующий фильтр — оверлей его скипал: drill без фильтра и без
  заголовка, ни одной ошибки (кейс `vendor_name` на вкладке «Пользователи»);
- фильтр без строчки в data flow — оверлей не попадал в WHERE: drill показывал
  неотфильтрованные тоталы, заголовок при этом заполнялся и маскировал баг
  (кейс `app_name` там же).

## Решение

Одна декларация — один источник правды:

1. **Бинд клика = собственная область оверлея.** Оверлей применяется к запросу
   слота, если фильтр есть в его строчном типе, — независимо от привязки в
   data flow (`CardCellDrillOverlay.FilterNames` + объединение в
   `QueryCompiler.AppendBoundFilters`). Data flow остаётся источником правды
   для сессионных фильтров (тулбар), а не для кликовых.
2. **Неизвестный бинд — ошибка парса.** `ClickBindingAnalyzer` (фаза валидации
   документа): каждый `set`/`drill` бинд обязан ссылаться на объявленный
   фильтр — громко, на загрузке, а не тихо на рендере.

Защита от неверной формы — уже существующий скип по строковому типу
(ADR типизированных флоу): фильтр, чьей колонки нет в типе строки слота, к
его запросу не применяется.

## Последствия

- Спека честна: забытое определение фильтра или привязка — ошибка загрузки,
  а не тихо пустой drill.
- Порядок типизации сохраняется: тип строки — контракт формы, бинд клика —
  контракт области оверлея, data flow — контракт сессионных фильтров.
- Строчка `app_name -> [app_name] users` в спеке остаётся допустимой
  (сессионная семантика), но больше не является обязательным условием для
  кликового drill.
