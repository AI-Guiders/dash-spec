# DASHSPEC-ADR-0125: DashSpec-managed views — публикация создаёт view в БД из флоу-графа

## Context

Авторская модель сегодня: берём БД, **руками пишем в ней view** (v_events,
v_usage_daily, …), потом подключаем DashSpec — `datasource sql` указывает на
эти view. То есть половина отчёта живёт вне спеки: логика агрегации/фильтрации
продублирована SQL-кодом, который не версионируется вместе с каталогом, не
проходит линт компилятора и невидима для навигации по графу.

При этом у нас уже есть всё, чтобы этот SQL **порождать**:

- флоу-граф умеет путешествовать по базе (ADR-0120): `source db → filter →
  group_by → order_by → projection` — компилятор сворачивает резолвящееся
  поддерево в один SELECT (пушдаун ADR-0121/0123 уже так работает);
- публикация уже компилирует артефакты из спеки: `dsc build types` →
  TypedRows.dll рядом с каталогом (ADR-0124). Симметрия очевидна: раз типы
  строк компилируются из `.ds`, то и view — могут.

Операторская метафора из которой это выросло: «в SQL есть temp-таблицы —
можно построить любую группировку программно». Managed views — то же, но
постоянные и управляемые публикацией, а не сессией.

## Decision

**Флоу с маркером `view` эмитится в БД как view.** Синтаксис (операторский,
2026-11-08): `module flow <name> view … end module` — автор явно маркирует
флоу; каждая source-цепочка модуля (source → трансформы → терминальный узел)
эмитится одним view:

```
module flow usage_report view

source sessions_by_hour {
  use provider analytics_db
  from table app.sessions              // базовая таблица, НЕ готовая view
  ports
    output rows: SessionHourRow
}
sessions_by_hour -> filter window -> group_by sessions_per_hour -> .
end module
```

`dsc build views` (и/или объединённый `dsc build`) эмитит
`CREATE OR ALTER VIEW dashspec_<flow>_<chain> AS <select>` в диалекте
коннектора источника. Reader читает готовую view вместо сборки запроса
по графу.

1. **Явный оп-ин, а не вывод движка.** Немаркированные флоу в БД не
   пишутся; `datasource sql` и ручные view остаются люком для непокрытых
   примитивов (см. Expressive power). Маркер решает и вопрос границы
   «наше/чужое»: `dashspec_`-префикс — только у эмитированного.
2. **DDL делает публикация, не хост.** Хост остаётся read-only-клиентом БД —
   это сохраняет действующее ограничение «хост не передеплоивается и не
   трогает схему». Права на `CREATE VIEW` — у учётки публикации. Смешение
   коннекторов внутри одной цепочки → громая ошибка компиляции (одна цепочка
   = один диалект).
3. **Идемпотентность.** Пересборка каталога пересоздаёт managed views тем же
   билдом; `dashspec_`-префикс = «производный артефакт, можно дропать
   префиксом». Drift между view и каталогом исключён конструкцией:
   view — функция ревизии, не состояние.
4. **Reader упрощается.** Точка чтения карточки = имя view; план выполнения
   кэшируется сервером БД; DBA видит глазами, что реально выполняется.
   Рукописные `v_*` в живых корпусах замещаются своими цепочками в
   `module flow … view`.

## Mechanics (набросок)

- Эмиттер живёт в компиляторе рядом с пушдауном: тот же резолвер поддерева,
   другой sink (DDL вместо параметризованного запроса).
- Коннектор-специфика DDL: PostgreSQL `CREATE OR REPLACE VIEW`, MS SQL
  `CREATE OR ALTER VIEW`, SQLite — пересоздание через DROP+CREATE. Уходит в
  SQL-dialect-слой (ADR-0006).
- Версионирование прод-каталогов: если в проде крутится старая ревизия, а
  билд уже накатил новые view — ломаем работающее. Кандидат-решения:
  ревизия-суффикс в имени (`..._r12`) + реестр живых ревизий, либо схема на
  ревизию. Решить до реализации (Open questions).
- Инспекция: `dsc build views --print` — показать эмитируемый DDL без
  применения (пайплайн-ревью, CI-диф).

## Consequences

- `+` SSOT: логика выборки целиком в спеке, версионируется и линтуется
  вместе с каталогом; исчезает класс ошибок «view в БД и спека разъехались».
- `+` Автору не нужен доступ к БД для аналитической логики: .ds + вьюхи БД
  только там, где автор сам решил выйти за граф (окна, CTE на полстраницы).
- `+` DBA-прозрачность: сгенерённый SQL виден и ревьюится как артефакт билда.
- `−` Публикации нужны DDL-права — новый класс среды (учётка билда ≠ учётка
  хоста). Там, где DDL-прав нет, управляемые view недоступны: фолбэк —
  ручные view, это не рантайм-ветка, а выбор автора на этапе проектирования.
- `−` Двойная поверхность в БД (наши view + чужие) — нужны конвенции имён и
  политика чистки осиротевших view при переименовании флоу. Граница подвижна:
  с добавлением узлов трансформаций ручные view сжимаются к нативным фичам
  диалекта (см. «Expressive power»).

## Expressive power и граница ручных view

Словарь db-трансформаций сегодня линеен и одно-табличен: WHERE, GROUP BY +
агрегаты, ORDER BY, LIMIT, проекция, DISTINCT. Но граф флоу — не цепочка:
**сложность растёт добавлением видов узлов, а не ограничена формой графа.**
Join/UNION — узлы с несколькими входами (граф держит fan-in), окна — узел с
эмитом `OVER (PARTITION BY …)`, каждый узел оборачивает предыдущий SELECT'ом
(композиция = view-on-view бесплатно).

Следствие для границы: **«двойная поверхность» — не постоянное свойство, а
функция от покрытия примитивов.** Ручные view — не вечный параллельный путь,
а костыль для непокрытого на сегодня (окна, self-join, рекурсивные CTE,
date-spine, UNION). Дорожная карта сужения границы = очередь новых узлов
трансформаций; `datasource sql` остаётся люком для нативных фич диалекта.

## Alternatives considered

- **Продолжать ручные view** — текущее состояние: логика вне спеки, drift
  руками. Отвергается как цель, остаётся как исключение по явной метке.
- **Materialized views / temp-таблицы на рантайме** — DDL на хост-пути,
  violates read-only host;_refresh-политики вне нашего контракта. Отвергнуто.
- **Inline SQL без view** (как сегодня читает raw-поток) — работает, но план
  не кэшируется, DBA слеп, автор не может переиспользовать выборку между
  карточками. остаётся механизмом чтения, view — стабильной поверхностью.

## Open questions (до статуса Accepted)

1. **Версионирование прод-ревизий**: суффикс `_rN` + реестр живых, схема на
   ревизию, или «одна живая ревизия, прод катится атомарно»?
2. ~~Граница ручных view~~ — **закрыто операторским синтаксисом**: явный
   маркер `module flow <name> view`; всё без маркера и без `dashspec_` —
   чужое, не трогаем.
3. **Собираем ли view для runtime-трансформеров** (ADR-0123 grouping:
   payload→payload после чтения) — нет, они по определению после SQL; но их
   database-пушдаун (order_by, ранние group_by) — входит в эмит.
4. **Каскад**: view на view (флоу читает managed view другого флоу)?
   Порядок создания, циклы.
5. **Мониторинг осиротевших**: `dsc build views --prune` — дропать
   dashspec_-view, на которые не ссылается текущая ревизия?

## Status

Proposed — идея оператора (2026-11-08); синтаксис `module flow <name> view`
закреплён (граница ручных view закрыта). До реализации — open question 1
(версионирование прод-ревизий).
