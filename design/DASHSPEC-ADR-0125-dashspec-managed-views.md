# DASHSPEC-ADR-0125: DashSpec-managed views — публикация создаёт view в БД из флоу-графа

## Context

Авторская модель сегодня: берём БД, **руками пишем в ней view** (v_events,
v_usage_daily, …), потом подключаем DashSpec — `datasource sql` указывает на
эти view. То есть половина отчёта живёт вне спеки: логика агрегации/фильтрации
продублирована SQL-кодом, который не версионируется вместе с каталогом, не
проходит линт компилятора и невидима для навигации по графу.

При этом у нас уже есть всё, чтобы этот SQL **порождать**:

- флоу-граф умеет путешествовать по базе (ADR-0120): `source db → filter →
  group_by → order_by → projection` — компилятор сворачивает резолвящееся
  поддерево в один SELECT (пушдаун ADR-0121/0123 уже так работает);
- публикация уже компилирует артефакты из спеки: `dsc build types` →
  TypedRows.dll рядом с каталогом (ADR-0124). Симметрия очевидна: раз типы
  строк компилируются из `.ds`, то и view — могут.

Операторская метафора из которой это выросло: «в SQL есть temp-таблицы —
можно построить любую группировку программно». Managed views — то же, но
постоянные и управляемые публикацией, а не сессией.

## Decision

**Флоу с маркером `view` эмитится в БД как view.** Синтаксис (операторский,
2026-11-08): `module flow <name> view … end module` — автор явно маркирует
флоу; каждая source-цепочка модуля (source → трансформы → терминальный узел)
эмитится одним view:

```
module flow usage_report view

source sessions_by_hour {
  use provider analytics_db
  from table app.sessions              // базовая таблица, НЕ готовая view
  ports
    output rows: SessionHourRow
}
sessions_by_hour -> filter window -> group_by sessions_per_hour -> .
end module
```

`dsc build views` (и/или объединённый `dsc build`) эмитит
`CREATE OR ALTER VIEW dashspec_<ns_slug>_<flow>_<chain>_<ast_sha8> AS <select>`
в диалекте коннектора источника (где `<ns_slug>` — нормализованный `namespace`
модуля флоу, а `<ast_sha8>` — первые 8 символов SHA-256 канонического AST
порождаемого запроса). Reader читает готовую view по этому детерминированному
имени вместо сборки запроса по графу на рантайме.

1. **Явный оп-ин, а не вывод движка.** Немаркированные флоу в БД не
   пишутся; `datasource sql` и ручные view остаются люком для непокрытых
   примитивов (см. Expressive power). Маркер решает и вопрос границы
   «наше/чужое»: `dashspec_`-префикс — только у эмитированного.
2. **Полная защита от коллизий при параллельной работе в DashSpec Studio (Content-Addressed Views + Leases).**
   Если два пользователя открыли каждый свой DashSpec Studio, нажали «New Project» (получив
   одинаковые дефолтные имена проекта/модуля и `module flow sameName view`) и подключились к
   одной БД `db_a`, любые человеческие имена (`project_id`, `namespace`, `flow`) совпадут.
   Но SQL `VIEW` (в отличие от таблицы) не хранит данных — это **чистая функция от текста `SELECT`**.
   Поэтому в `db_a` физические вьюхи адресуются **по содержимому (Content-Addressed)**:
   - **Физическое имя view = `dashspec_<flow>_<chain>_<ast_sha12>`** (где `<ast_sha12>` — 12 символов
     SHA-256 от канонического AST `SELECT`-запроса):
     1. **Разные запросы = разные физические имена view:** если Пользователь 1 и Пользователь 2
        написали разную логику в одноимённом `flow sameName view`, у них разные `<ast_sha12>`
        (`..._4a8f9c120b3e` и `..._7d2e1190fa44`). Они физически не могут затереть или испортить
        view друг друга через `CREATE OR ALTER VIEW`.
     2. **Одинаковые запросы = безопасный общий артефакт:** если оба написали идентичный запрос,
        `<ast_sha12>` совпадает, и тело `SELECT` байт-в-байт одно и то же.
   - **Учёт ссылок (Leases) по `project_uid` для безопасного `--prune`:**
     При создании проекта DashSpec Studio генерирует в `.dsproj` уникальный `project_uid` (UUID,
     аналог `ProjectGuid`). В БД ведётся таблица ссылок
     `dashspec_view_leases (view_name, project_uid, updated_at_utc, PRIMARY KEY (view_name, project_uid))`:
     - публикация проекта обновляет только строки своего `project_uid`;
     - `dsc build views --prune` удаляет физическую `VIEW` из БД **только тогда, когда на неё
       не осталось ни одной активной ссылки (`COUNT(project_uid) == 0`)** — поэтому сборка мусора
       у Пользователя 1 никогда не удалит живые вьюхи Пользователя 2.
3. **Граница применимости плоской `VIEW` vs параметризованной `iTVF` (фильтры до свёртки).**
   Плоская SQL `VIEW` не принимает рантайм-параметров (`@p0`), поэтому внешний `WHERE`
   карточки накладывается *после* тела view (`SELECT * FROM dashspec_... WHERE ...`).
   - Если фильтр карточки привязан к колонке, которая **сохранена в выходном типе view** (входит в ключ `by` у `summarize`, и в цепи нет `window`/`limit`, зависящих от фильтра), оптимизатор СУБД проталкивает внешний `WHERE` сквозь `VIEW` в базовую таблицу (predicate pushdown).
   - Если же фильтр входит в граф **до** `summarize` по неключевой колонке (которая схлопывается при агрегации) или **до** `window` (`OVER (...)`) / `top`, плоская `VIEW` семантически неприменима: внешний `WHERE` либо не найдёт колонку, либо отфильтрует уже посчитанный по всей истории ранг. В этом случае компилятор либо эмитит **Inline Table-Valued Function (`iTVF`)** (`CREATE OR ALTER FUNCTION dashspec_...(@p0 ...) RETURNS TABLE AS RETURN (SELECT ...)`), которую оптимизатор СУБД инлайнит как параметризованную view с сохранением Index Seek, либо выдаёт ошибку компиляции при попытке скомпилировать такую цепь в безпараметрическую `VIEW`.
4. **DDL делает публикация, не хост.** Хост остаётся read-only-клиентом БД —
   это сохраняет действующее ограничение «хост не передеплоивается и не
   трогает схему». Права на `CREATE VIEW` — у учётки публикации. Смешение
   коннекторов внутри одной цепочки → громкая ошибка компиляции (одна цепочка
   = один диалект).
5. **Идемпотентность.** Пересборка каталога пересоздаёт managed views тем же
   билдом; `dashspec_`-префикс = «производный артефакт, можно дропать
   префиксом». Drift между view и каталогом исключён конструкцией:
   view — функция ревизии, не состояние.
6. **Reader упрощается.** Точка чтения карточки = имя view; план выполнения
   кэшируется сервером БД; DBA видит глазами, что реально выполняется.
   Рукописные `v_*` в живых корпусах замещаются своими цепочками в
   `module flow … view`.

## Mechanics (набросок)

- Эмиттер живёт в компиляторе рядом с пушдауном: тот же резолвер поддерева,
   другой sink (DDL вместо параметризованного запроса).
- Коннектор-специфика DDL: PostgreSQL `CREATE OR REPLACE VIEW`, MS SQL
  `CREATE OR ALTER VIEW`, SQLite — пересоздание через DROP+CREATE. Уходит в
  SQL-dialect-слой (ADR-0006).
- Версионирование прод-каталогов: если в проде крутится старая ревизия, а
  билд уже накатил новые view — ломаем работающее. Кандидат-решения:
  ревизия-суффикс в имени (`..._r12`) + реестр живых ревизий, либо схема на
  ревизию. Решить до реализации (Open questions).
- Инспекция: `dsc build views --print` — показать эмитируемый DDL без
  применения (пайплайн-ревью, CI-диф).

## Consequences

- `+` SSOT: логика выборки целиком в спеке, версионируется и линтуется
  вместе с каталогом; исчезает класс ошибок «view в БД и спека разъехались».
- `+` Автору не нужен доступ к БД для аналитической логики: .ds + вьюхи БД
  только там, где автор сам решил выйти за граф (окна, CTE на полстраницы).
- `+` DBA-прозрачность: сгенерённый SQL виден и ревьюится как артефакт билда.
- `−` Публикации нужны DDL-права — новый класс среды (учётка билда ≠ учётка
  хоста). Там, где DDL-прав нет, управляемые view недоступны: фолбэк —
  ручные view, это не рантайм-ветка, а выбор автора на этапе проектирования.
- `−` Двойная поверхность в БД (наши view + чужие) — нужны конвенции имён и
  политика чистки осиротевших view при переименовании флоу. Граница подвижна:
  с добавлением узлов трансформаций ручные view сжимаются к нативным фичам
  диалекта (см. «Expressive power»).

## Expressive power и граница ручных view

Словарь db-трансформаций сегодня линеен и одно-табличен: WHERE, GROUP BY +
агрегаты, ORDER BY, LIMIT, проекция, DISTINCT. Но граф флоу — не цепочка:
**сложность растёт добавлением видов узлов, а не ограничена формой графа.**
Join/UNION — узлы с несколькими входами (граф держит fan-in), окна — узел с
эмитом `OVER (PARTITION BY …)`, каждый узел оборачивает предыдущий SELECT'ом
(композиция = view-on-view бесплатно).

Следствие для границы: **«двойная поверхность» — не постоянное свойство, а
функция от покрытия примитивов.** Ручные view — не вечный параллельный путь,
а костыль для непокрытого на сегодня (окна, self-join, рекурсивные CTE,
date-spine, UNION). Дорожная карта сужения границы = очередь новых узлов
трансформаций; `datasource sql` остаётся люком для нативных фич диалекта.

### Expressive power по диалектам (параметризованный артефакт ≠ везде)

«Параметризованная разворачиваемая view» (см. п.3: границы плоской `VIEW` vs
`iTVF`) переносима не на все СУБД — эмиссия **функция от диалекта коннектора**:

| Диалект | Параметризованный артефакт | Инлайнится оптимизатором |
|---|---|---|
| SQL Server (tsql) | iTVF (`RETURNS TABLE AS RETURN (…)`) | ✅ |
| PostgreSQL | `LANGUAGE sql` set-returning function (`STABLE`) | ✅ (не `PL/pgSQL` — он чёрный ящик) |
| Oracle 23c+ | `SQL_MACRO (TABLE)` | ✅ |
| Oracle <23c | pipelined function | ❌ (MSTVF-класс) |
| DB2 LUW | inline SQL table function | ✅ |
| MySQL / MariaDB | **нет табличных функций на SQL** | — (только плоские views + внешний `WHERE`) |
| SQLite | C-API table-valued functions | n/a (не декларируется на SQL) |

Следствие: для диалектов без инлайнимого артефакта (MySQL-класс) цепочки
«фильтр до свёртки/окна» **не эмитят БД-артефакт** — reader читает их
генерацией запроса по графу (нынешний механизм), `dsc build views`
пропускает только плоско-выразимые цепи. Это не падение фичи, а честное
per-dialect сужение той же границы из п.3.

## Alternatives considered

- **Продолжать ручные view** — текущее состояние: логика вне спеки, drift
  руками. Отвергается как цель, остаётся как исключение по явной метке.
- **Materialized views / temp-таблицы на рантайме** — DDL на хост-пути,
  violates read-only host;_refresh-политики вне нашего контракта. Отвергнуто.
- **Inline SQL без view** (как сегодня читает raw-поток) — работает, но план
  не кэшируется, DBA слеп, автор не может переиспользовать выборку между
  карточками. остаётся механизмом чтения, view — стабильной поверхностью.

## Open questions (до статуса Accepted)

1. ~~**Версионирование прод-ревизий**~~ — **закрыто content-addressing**: физическое
   имя — функция ревизии (`ast_sha12`), а не запись о ней. Новый билд никогда не
   перезаписывает старую view (другой SELECT → другое имя; append-only
   пространство имён), старая ревизия каталога продолжает вычислять своё имя и
   читать свою физически живую view — ревизии сосуществуют в одной БД без
   реестра. Одинаковое имя = байт-в-байт одинаковое тело, drift невозможен по
   построению. Суффиксы `_rN`/реестры живых ревизий нужны были бы только для
   человеческих имён — отпадают. Остаток — не версионирование, а гигиена:
   сборка мусора осиротевших view (`--prune` по leases + политика запуска/TTL,
   см. вопрос 5).
2. ~~Граница ручных view~~ — **закрыто операторским синтаксисом**: явный
   маркер `module flow <name> view`; всё без маркера и без `dashspec_` —
   чужое, не трогаем.
3. **Собираем ли view для runtime-трансформеров** (ADR-0123 grouping:
   payload→payload после чтения) — нет, они по определению после SQL; но их
   database-пушдаун (order_by, ранние group_by) — входит в эмит.
4. **Каскад**: view на view (флоу читает managed view другого флоу)?
   Порядок создания, циклы.
5. **Мониторинг осиротевших**: `dsc build views --prune` — дропать
   dashspec_-view, на которые не осталось активных leases (запись leases уже
   реализована; осталось: сама команда prune + политика запуска/TTL)?

## Future extensions (аннотация, не Decision)

- **Вывод индексов.** Эмиттер знает профиль доступа каждого SELECT (он его
  сам построил): колонки WHERE → composite-кандидаты, GROUP BY/ORDER BY →
  сортирующие, плюс покрывающие (`INCLUDE` / covering). Кардинальность —
  из EXPLAIN/статистик на шаге публикации. Режим — **recommend, не
  auto-create**: `dsc build indexes --print` эмитит DDL-кандидатов с
  обоснованием (запрос → колонка → индекс); решение за человеком — индекс
  не производный артефакт, а физический дизайн с write-amplification.
  Обязательно: дедуп по префиксному совпадению (один `(a,b)` вместо
  `(a)`,`(a,b)`,`(a,b,c)`), диалектные фичи (INCLUDE, partial/filtered).
