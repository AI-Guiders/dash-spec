# DASHSPEC-ADR-0120: Фильтры — узлы графа потоков (transform с типизированным параметром)

## Context

Механика фильтров — старейший слой DSL, она предшествует графу потоков,
трансформациям, типизации и источникам. Пока вокруг неё вырос dashflow, фильтры
остались до-графовой конструкцией с четырьмя осями (ADR-0037):

| Ось | Сегодня |
|---|---|
| bind | декларация колонки по имени: `bind field column = table.col` |
| show | label/widget/ref |
| видимость | `toolbar` / `page toolbar` / `card filters` → `DashboardFilters` vs `LocalFilters` |
| layout | `card layout [...]` |

Цена этой архитектуры — не абстрактная. Конкретный кейс (внутренний отчёт из
закрытого контент-репо, 2026-11-06,
полную трассу см. [ADR-0119](DASHSPEC-ADR-0119-filter-options-data-domain.md)):
выбор продукта из фильтра схлопывает матрицу, потому что опции фильтра грузятся
без скоупа (`SELECT DISTINCT` по словарю таблицы на бутстрапе), а данные
карточки — с её локальным периодом. Список обещает ~40 продуктов, матрица в
выбранном дне показывает 25; разница — мёртвые продукты, и их выбор лежит на
самом виду.

ADR-0119 разбирал этот кейс и пришёл к скоуп-модели («экземпляр фильтра
принадлежит скоупу: report или card»). Но скоуп-модель — симптоматическое
лечение: она ставит правильную семантику **внутри до-графовой механики**. Пока
шли обсуждения, стало ясно, что у модели есть носитель, который делает все
её случаи частными: **граф потоков**.

## Наблюдение (основа решения)

Фильтр по сути — это **transform-узел графа, который влияет на поток**, плюс
типизированный параметр (значение виджета). Всё, что сегодня выражено осями
ADR-0037, в терминах dashflow (ADR-0078/0079/0094) выражается естественнее:

- **bind** → входное ребро. Подключил `events_tz -> event_type_filter` — фильтруешь тот поток, который подключил. Колонка берётся из
  типа, а не по имени: несовместимость параметра с полем UDT — compile-time
  диагностик со спаном (готовая механика ADR-0079).
- **скоуп** → размещение узла в графе. Узел на report-flow — report-scope
  (одно состояние, все потребители вниз по рёбрам). Узел на card-flow —
  card-scope (свой экземпляр, своё состояние, свой вход). Именно скоуп-модель
  ADR-0119, но не как ось реестра, а как свойство графа по построению.
- **опции** → distinct по **входному потоку узла** — просто ещё один transform
  ниже по течению. Card-scope: вход = поток карточки с её периодом → список
  ровно совпадает с матрицей. Report-scope: вход — общий поток → union
  автоматически, без специальной логики.
- **видимость/layout** → презентация параметра. Узел графа + `show` (виджет на
  тулбаре репорта или в карточке) — тот же паттерн, что диаграмма + presentation
  (ADR-0007). Четыре оси схлопываются в две: **узел в графе** + **презентация
  параметра**.

## Decision (draft, на обсуждение)

**Фильтр = типизированный transform-узел графа.**

### Sugar поверх IR: авторский синтаксис не меняется (решено)

Графовая модель — это **IR**, а не целевой авторский синтаксис. Автор пишет
спеку как раньше (`bind field` / `filters` / `toolbar` / `series max`) —
транспилятор синтезирует узлы и рёбра: `bind` → ребро, `card filters` →
размещение в card-flow, `series max` → `tail_reduce`-узел с tap'ами. Всё, что
чинит этот ADR (домен опций из входного потока, locality, типизация,
инертный выбор), живёт в IR; снаружи граф не усложняется. Explicit-узловая
форма (примеры ниже) — **escape hatch** для топологий, которые sugar не
выражает (например, двухуровневый список через два ребра), не целевой
синтаксис.

Контракт Designer'а (ADR-0078): дизайнер мутирует ту же FlowGraph IR, при
сохранении изменения **десугаризируются обратно** в минимальный sugar;
синтезированные узлы показываются свёрнутыми группами и не требуют
авторского синтаксиса для своего существования.

IR-форма (escape hatch):

```text
transformer event_type_filter {
  ports
    input  rows: EventRow               // поток, который фильтруем
    output rows: EventRow               // отфильтрованный
    param  event_type: string = all     // значение виджета — типизированный скаляр
  end ports
}
```

Подключение — обычный синтаксис рёбер:

```text
report
  data flow
    events_tz -> event_type_filter -> card.events.diagram
    event_type_filter -> [toolbar] chrome.card.events          // презентация: где виджет
  end data flow
end report
```

Card-scope — тот же узел, объявленный/подключённый в card-flow карточки:

```text
card activity
  data flow
    local event_type_filter -> diagram
    event_type_filter -> [toolbar] chrome.card.events
  end data flow
end card
```

### Правила

1. **Состояние** — у экземпляра узла. Одинаковые id на report-flow и card-flow
   легальны (одноимённые переменные разных скоупов); разрешение однозначно по
   месту. Иерархия фиксированная (report → card), теневого поиска ближайшего
   объявления нет.
2. **Типизация — по ADR-0079**: `param` — примитив или UDT-поле; вход/выход —
   `rows R`. Несовместимость `param` с полем входного потока — ошибка компиляции
   графа, не runtime.
3. **Опции** — transform на входном потоке узла: distinct по входу в его
   (входном) периоде. Лениво при первом открытии виджета, кэш по
   `{узел}:{от потока}:{период}`. Словарная деградация — для узла без входного
   ребра (филируется напрямую источником по колонке — это должно ловиться
   линтом как редкий легаси-случай).
4. **ADR-0099 поглощается**: `ReportFieldOptionsLoader` становится этим
   downstream-transform'ом; контракт «поле + `CanLoadDistinctFieldOptions`»
   заменяется проверкой входного ребра.
5. **Миграция — транспиляция сразу, без окна двойной поддержки** (решено в
   обсуждении, уточнено sugar-решением): legacy-синтаксис
   (`filter/bind/filters/card filters/bind` на card) транспилируется в новую
   IR на чтении — декларация → узел с param-портом, `card bind` → ребро,
   `card filters` → card-flow размещение. Один парсер; runtime второй механики
   не получает. Legacy-синтаксис **не депрекируется**: sugar — постоянная
   поверхность авторинга (см. §«Sugar поверх IR»), узловая форма — escape
   hatch.
6. **ADR-0062 (stale-значения)**: при смене входного потока значение параметра,
   отсутствующее в новом домене, хранится серым и в SQL не идёт — деталь
   семантики параметра, остаётся на обсуждение.


### Tail reduce: «Другие» / `series max` — трансформация, не фича фильтра (решено)

`series max` сегодня — скрытая свёртка внутри рендера. В графовой модели она
становится явным агрегирующим transform-узлом (автор по-прежнему пишет
`series max = 12`; узел синтезируется — см. §«Sugar поверх IR»):

```text
events_tz -> event_type_filter -> tail_reduce -> card.events.diagram

tail_reduce:
  transform use reduce { by = series, top = 12, tail = "Другие (N)" }
```

Все три потребителя подключаются к нужным портам — топология вместо режимов:

- **опции виджета** = distinct по входу фильтра (tap до reduce) → полный домен;
- **матрица** = выход reduce → «как на диаграмме»;
- **двухуровневый список** («базовый distinct + запись „Другие (N)“») — не особый
  режим виджета, а два ребра: distinct с сырого потока + одно значение с выхода
  reduce; виджет объединяет;
- **выбор «Другие»** в фильтре получает честную семантику: параметр уходит в
  reduce-узел (tail-фильтр), а не в диаграмму.

Vocabulary — без изменений в ядре: transform-плагины расширяют язык тем же
механизмом, что presentation-vocabulary (plugin-declared grammar knobs,
contributor registry + auto-discovery, ADR-0080). `reduce` — новый
transform-плагин, объявляющий свои свойства; компилятор графа получает
зависимость «опции-узел ↔ param» из типизации портов (ADR-0079).


### «Когда данных нет» — состояние в семье `when` (решено)

Период без данных → distinct по входному потоку возвращает ноль строк. Это не
новая механика: у карточек уже есть precondition-семья `when` (ADR-0030,
`when filter` / `when filter.empty` / `when filter { message }`). Домен опций
param-узла добавляет в неё одно состояние — `.no_data`:

```text
card activity {
  when event_type.no_data {
    message = "Нет данных в выбранном периоде"
  }
  ...
}
```

- дефолт (без `when`) — честное пусто: список опций пуст, сохранённый выбор
  пользователя — серым (стыкуется с ADR-0062 / OQ5);
- авторская надпись/placeholder — через `when … { message = "…" }`, как для
  пустых фильтров;
- режимы «держать прошлый список» / «показать весь словарь» сознательно не
  вводятся (YAGNI): заведём отдельными формами, только если реальный автор
  попросит.

Принцип: одна precondition-механика на все «пустые» состояния — домена опций,
значения фильтра, периода; никаких параллельных enum-параметров. И правило
именования остаётся: авторские конструкции читаются как фразы предметного
языка.


### Execution locality: `database` vs `runtime` (решено, ядро модели)

DataFlow — это ETL, и граф стоит **над источником данных, а не вместо него**.
Если фильтрация исполняется в рантайме, мы делаем `SELECT` без `WHERE` и
фильтруем в памяти — то, что умеет СУБД, должна делать СУБД. Поэтому каждая
трансформация объявляет свою локальность исполнения:

- **`database`** (push-down): узел компилируется внутрь запроса источника.
  Параметрические фильтры (включая date-param), `reduce`/top-tail (это TOP +
  GROUP BY на стороне SQL), distinct опций — всё это участвует в сборке
  исходного `SELECT ... WHERE ... TOP ...`, ровно как сегодняшний
  QueryCompiler. «Фильтр как узел» = **узел сборки запроса**, не строчный
  фильтр в памяти. Название — про место исполнения; «source» не подходит,
  потому что в графе source — это уже узлы-источники.
- **`runtime`**: исполнение в пайплайне после загрузки. `to_zone` (сдвиг
  часового пояса для отображения) — дёшево и честно в рантайме.

**Hoisting — обязанность компилятора, не автора.** Компилятор складывает все
`database`-узлы пути в один запрос к источнику и сам поднимает их к началу
пути. Подъём легален, когда типизация портов (ADR-0079) доказывает
коммутативность: промежуточные `runtime`-узлы не трогают колонку/тип, по
которым фильтрует поднимаемый узел. Не может поднять — **loud error**, а не
тихий split на два запроса: «`hour_filter` не может уехать в запрос, потому
что его колонку создаёт `to_zone` (runtime)» — автор либо меняет топологию,
либо выбирает runtime-локальность узла. Для легаси-цепочек (фильтры сразу за
источником, как сегодня в QueryCompiler) hoisting тривиален и поведение 1:1.

Цена: исполнение может не совпадать с порядком узлов в тексте. Компенсация —
Designer/превью показывает execution-группировку (database-блок /
pipeline-блок). Словарь локальностей расширяется только через ADR.


### Инертный выбор значений (решено, OQ5 / ADR-0062)

Значение параметра, отсутствующее в текущем домене (сузился период, опустел
домен, переименовался продукт), **хранится, но не применяется**:

- значение остаётся в сессии и видно в виджете — серым/неактивным, с тултипом
  с причиной («нет в выбранном периоде»);
- в compiled-запрос не попадает: WHERE по нему не строится, данные честные;
- один клик — снял; домен вернулся (период вернули) — значение снова кликабельно.

Семантика универсальна для параметров любого типа (string, daterange) и любого
скоупа (report/card) — это свойство класса «параметр», не отдельная механика
фильтров. Молча сбрасывать нельзя (пользователь теряет контекст), молча
оставлять активным нельзя (скрытое состояние, худший вариант).


### Период: чей диапазон фильтрует карточку (решено)

Период — обычный param-узел типа `daterange` (см. OQ4), поэтому вопрос
«общий период vs период карточки» решается топологией, без специальной
переменной. Три состояния — два из них бесплатны, одно задаётся явно:

- **нет своего `bind date`** — карточка питается от репортового потока и
  получает период репорта по построению; синтаксис не нужен;
- **есть свой `bind date`** — период карточки независим (`independent`,
  по умолчанию; слово можно не писать — это сегодняшнее поведение локальной
  даты), репортовый календарь её потоки не трогает;
- **есть свой `bind date`, но внутри репортового** — единственный authored-
  случай: ограничение задаётся **на самом фильтре**, полем в его declarative-
  таблице (`within report`): виджет режет допустимый диапазон по репортовому
  периоду, данные считаются пересечением.

В IR `within` — свойство param-узла «домен этого параметра ограничен другим
параметром (вышестоящим период-узлом)». Механизм общий, не датовый спец-кейс:
«опции продукта, ограниченные выбранной платформой» — та же конструкция.
Переопределение периода — это замена точки подключения потока, не пересечение
диапазонов; кто чей период видит, выводится из топологии рёбер.


Замечание по эргономике рёбер (дискуссия 2026-11-07; касается только
escape hatch-формы — в sugar рёбер для автора нет): скобочная форма
`A[rows] -> [rows]B` — не типы, а **уточнение имени порта** (у узла может быть
несколько портов, например `default` + `stream`); типы объявляются в
определении трансформера. Рёбра с дефолтным портом пишутся голыми —
mermaid-конвенции: типы живут в узлах, рёбра читаются как картина.
## Alternatives considered

- **Скоуп-модель поверх текущей механики** (ADR-0119): ось «видимость» → ось
  «скоуп», резолюция домена опций в loader'е. Закрывает кейс схлопывания, не
  трогая парсер. Отклонено как цель, принята как ступень: это симптоматическое
  лечение — правильная семантика внутри до-графовой архитектуры, которую потом
  пришлось бы переделывать. ADR-0119 → superseded by this.
- **`distinct_scope` в декларации фильтра** (первый draft ADR-0119): ещё одна
  декларация в осях, дублирующая то, что граф уже знает. Отклонено.
- **Оставить как есть + дизейбл отсутствующих опций**: полумера, пользователь
  видит мусор. Отклонено.

## Consequences

- `+` корень кейса схлопывания исчезает по построению: домен опций = входной
  поток узла, рассинхрон невозможен архитектурно.
- `+` типизация фильтров приходит бесплатно: ошибки «колонка не существует /
  тип не тот» — compile-time (ADR-0079), а не пустая диаграмма в рантайме.
- `+` четыре оси ADR-0037 схлопываются в две; «видимость» перестаёт быть
  отдельной концепцией.
- `+` авторский синтаксис не меняется: унификация механики живёт в IR,
  sugar — постоянная поверхность авторинга; миграция авторов не требуется.
- `−` большой рефактор: парсер, IR, сессия значений, тулбары, Data Flow
  Designer. Компенсируется отсутствием промежуточной заплатки, которую потом
  пришлось бы выкидывать.
- `−` миграция существующих спек — транспиляция legacy-синтаксиса
  на чтении; sugar — постоянная поверхность авторинга, миграция не требуется.

## Open questions (все решены)

1. ~~**Миграционный график**~~ — решено: транспиляция legacy→узлы сразу, без
   двойной поддержки (см. Decision §5).
2. ~~**«Другие» / `series max`**~~ — решено (см. Decision §«Tail reduce»): это не
   вопрос фильтров, а точка tap'а на графе.
3. ~~**Пустой домен**~~ — решено: переиспользуем семью `when` (ADR-0030) —
   новое состояние `.no_data` у param-узла (см. Decision §«Когда данных нет»).
4. ~~**Date-фильтры как param-узлы**~~ — решено: дата перестаёт быть особым
   видом фильтра (`bind date`) и становится param-узлом с типом `daterange`;
   календарь/диапазоны/`today` — презентация параметра; локальность —
   `database` (значение уезжает в WHERE compiled-запроса). Grain
   (`day/month/year`) —
   свойство потока/диаграммы, не фильтра.
5. ~~**ADR-0062**~~ — решено: инертный выбор (см. Decision §«Инертный выбор
   значений»); универсальная семантика для параметров любого типа.
