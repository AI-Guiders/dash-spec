# DASHSPEC-ADR-0120: Фильтры — узлы графа потоков (transform с типизированным параметром)

## Context

Механика фильтров — старейший слой DSL, она предшествует графу потоков,
трансформациям, типизации и источникам. Пока вокруг неё вырос dashflow, фильтры
остались до-графовой конструкцией с четырьмя осями (ADR-0037):

| Ось | Сегодня |
|---|---|
| bind | декларация колонки по имени: `bind field column = table.col` |
| show | label/widget/ref |
| видимость | `toolbar` / `page toolbar` / `card filters` → `DashboardFilters` vs `LocalFilters` |
| layout | `card layout [...]` |

Цена этой архитектуры конкретна (внутренний отчёт, 2026-11-06, трасса в
[ADR-0119](DASHSPEC-ADR-0119-filter-options-data-domain.md)): выбор продукта из
фильтра схлопывает матрицу, потому что опции грузятся без скоупа (`SELECT
DISTINCT` по словарю таблицы на бутстрапе), а данные карточки — с её локальным
периодом. Список обещает ~40 продуктов, матрица в выбранном дне показывает 25;
разница — мёртвые продукты, и их выбор лежит на самом виду.

ADR-0119 разбирал кейс и предложил скоуп-модель. Она закрывает симптом, но
оставляет правильную семантику внутри до-графовой механики, которую пришлось бы
потом переделывать. У модели есть носитель, делающий все её случаи частными:
**граф потоков**.

## Decision

**Фильтр — типизированный transform-узел графа с param-портом.** Всё, что сегодня
выражено осями ADR-0037, выражается топологией и типами:

- **bind** → входное ребро. Колонка берётся из типа потока, а не по имени;
  несовместимость — compile-диагностик со спаном (ADR-0079).
- **скоуп** → размещение узла: report-flow — report-scope (одно состояние, все
  потребители вниз по рёбрам), card-flow — card-scope (свой экземпляр и вход).
  Иерархия фиксированная (report → card), теневого поиска нет.
- **опции** → distinct по входному потоку узла. Card-scope: вход = поток карточки
  с её периодом → список совпадает с матрицей по построению. Лениво при первом
  открытии виджета. Словарная деградация (фильтр напрямую от источника) — линт.
- **видимость/layout** → презентация параметра (виджет тулбара/карточки), тот же
  паттерн, что диаграмма + presentation (ADR-0007).

Четыре оси схлопываются в две: **узел в графе** + **презентация параметра**.

### Авторский синтаксис — sugar поверх IR

Авторский синтаксис не меняется: таблица `filters`, `bind`, `card filters`,
`series max` — постоянная поверхность авторинга. Транспилятор на чтении
синтезирует узлы и рёбра IR: `bind` → ребро, `card filters` → размещение в
card-flow, `series max` → `tail_reduce`-узел. Явная узловая форма существует
только как escape hatch для топологий, которые sugar не выражает; целевым
авторским синтаксисом она не является, и легаси не депрекируется.

Единственное расширение таблицы — колонка **`depends`** (каскадные домены):

```text
filters
  | id       | bind  | column              | label     | widget   | ref      | range | depends        |
  | platform | field | v_activity.platform | Платформа | combobox | platform | -     | -              |
  | product  | field | v_activity.product  | Продукт   | combobox | product  | -     | platform       |
end filters
```

`depends = X` (id соседа или `report.<id>`) означает: домен этого фильтра
ограничен текущим значением X. Предикат выводится из типов (field — равенство в
distinct-запросе опций, date — рамки диапазона); в IR это scalar-ребро
зависимости между param-узлами. Механизм общий: «период карточки в рамках
репортового» и «продукты выбранной платформы» — одна конструкция.

Период подчиняется тем же правилам топологии: нет своего `bind date` — карточка
питается от репортового потока и получает период репорта; есть свой — период
карточки независим (сегодняшнее поведение, дефолт); свой + `depends =
report.<id>` — период карточки ограничен рамками репортового, данные —
пересечение. Переопределение периода — замена точки подключения потока, не
пересечение диапазонов.

### Трансформации автора: `transforms on <узел>`

```text
transforms on events_tz
  time_tz { tz = session }
  rename { from = "app", to = "product" }
end transforms
```

Блок = цепочка трансформ на дефолтном выходе узла, порядок сверху вниз; явное
ребро от того же узла цепляется к выходу блока; несколько блоков на один узел —
lint «объедини». Точка подключения при ветвлении уточняется портом в заголовке
(`transforms on events_tz [by_product]`) — тот же механизм, что уточнение рёбер
ADR-0091; в линейной цепочке уточнение не нужно. Параметры трансформа — в его
блоке; порты sugar'у не нужны.

### Execution locality: `database` / `runtime`

Каждая трансформация объявляет локальность исполнения — контракт **определения**,
не точки использования:

- **`database`** (push-down): узел компилируется внутрь запроса источника —
  параметрические фильтры, date-параметры, `reduce`/top-tail (TOP + GROUP BY),
  distinct опций. Название — про место исполнения; «source» не подходит, потому
  что source в графе — уже узлы-источники.
- **`runtime`**: исполнение в пайплайне после загрузки (`to_zone` и т.п. —
  дёшево и честно в рантайме).

Компилятор сворачивает все `database`-узлы пути в один запрос и сам поднимает их
к началу пути (hoisting — обязанность компилятора). Подъём легален, когда
типизация портов (ADR-0079) доказывает коммутативность: промежуточные
`runtime`-узлы не трогают колонку/тип поднимаемого узла. Не может поднять —
loud error («`hour_filter` не может уехать в запрос: его колонку создаёт
`to_zone` (runtime)»), не тихий split. Designer/превью показывает
execution-группировку (database-блок / pipeline-блок). Словарь локальностей
расширяется только через ADR.

### Дата, «Другие», пустой домен, инертный выбор

- **Дата** — не особый вид фильтра: param-узел типа `daterange`; календарь,
  диапазоны, `today` — презентация параметра; локальность `database`. Grain
  (`day/month/year`) — свойство потока/диаграммы, не фильтра.
- **«Другие» / `series max`** — агрегирующий transform-узел `tail_reduce`,
  синтезируемый из sugar. Топология вместо режимов: опции виджета — tap до
  reduce (полный домен), матрица — выход reduce («как на диаграмме»); выбор
  «Другие» уходит параметром в reduce-узел, а не в диаграмму. Гибридный список
  («топ-N + узел „Другие (M)“») — дерево в презентации параметра: полный домен
  минус топ, разность считается виджетом. `reduce` — transform-плагин; язык
  расширяется тем же механизмом, что presentation-vocabulary (ADR-0080).
- **Пустой домен** — состояние `.no_data` в существующей семье `when`
  (ADR-0030): `when event_type.no_data { message = "…" }`. Дефолт без `when` —
  честное пусто, сохранённый выбор — серым. Режимы «держать прошлый список» /
  «весь словарь» сознательно не вводятся (YAGNI).
- **Инертный выбор** (ADR-0062): значение, отсутствующее в текущем домене,
  хранится, но не применяется — серым/неактивным с тултипом причины, в
  compiled-запрос не попадает, один клик — снял, домен вернулся — снова
  кликабельно. Универсально для параметров любого типа и скоупа; молча
  сбрасывать и молча оставлять активным нельзя.

### Текст спеки — проекция графа документа

SSOT документа — собственный граф DashSpec: `ParseTree` (Modeling.Parse/Syntax)
несёт полный текст, AST со спанами и токены; пустые строки и комментарии —
first-class узлы (lossless по построению). Parse (текст→граф) и print
(граф→текст) — два направления одной проекции; разъехаться они не могут. Print —
спан-хирургия: правка узла = вырезать спан и вклеить новый текст, остальное
байт-в-байт; требования каноничности print нет. Designer (ADR-0078) мутирует ту
же IR и сохраняет через print; синтезированные узлы показывает свёрнутыми
группами. Code Center (`DocumentGraphBridge`) — адаптер-потребитель графа
документа. Потоковый IR (`DashflowTypes` и семья) — внутреннее представление без
текста и спанов; проекция на него не опирается.

### Миграция

Транспиляция legacy в IR на чтении, без окна двойной поддержки: один парсер,
вторая механика в рантайме не заводится. Диагностики маппятся на строки исходной
спеки (спаны), не на синтезированный IR. Миграция авторов не требуется — sugar
постоянен.

## Alternatives considered

- **Скоуп-модель поверх текущей механики** ([ADR-0119](DASHSPEC-ADR-0119-filter-options-data-domain.md)):
  ось «видимость» → ось «скоуп», резолюция домена опций в loader'е. Закрывает
  кейс схлопывания, не трогая парсер; симптоматическое лечение внутри
  до-графовой архитектуры, которую пришлось бы переделывать. Superseded by this.
- **`distinct_scope` в декларации фильтра** (первый draft ADR-0119): ещё одна
  декларация в осях, дублирующая то, что граф знает сам. Отклонено.
- **Узловая форма как целевой авторский синтаксис**: явные рёбра для фильтров
  читаются хуже цепочек и дублируют то, что sugar уже выражает; граф остаётся
  IR, язык автора не растёт. Отклонено; явная форма — только escape hatch.
- **Оставить как есть + дизейбл отсутствующих опций**: полумера, пользователь
  видит мусор. Отклонено.

## Consequences

- `+` корень кейса схлопывания исчезает по построению: домен опций = входной
  поток узла, рассинхрон невозможен архитектурно.
- `+` типизация фильтров бесплатно: «колонка не существует / тип не тот» —
  compile-time (ADR-0079), не пустая диаграмма в рантайме.
- `+` каскадные домены (`depends`) — общий механизм, закрывающий и date-in-report,
  и межфильтровые зависимости одним ребром.
- `+` производительность охранена контрактом локальности: СУБД делает то, что
  умеет СУБД; hoisting и его loud errors контролируют деградацию.
- `+` авторский синтаксис не меняется; миграция авторов не требуется.
- `−` большой рефактор: парсер, IR, сессия значений, тулбары, Designer.
  Компенсируется отсутствием промежуточной заплатки.
- `−` модель за sugar'ом глубже (locality, hoisting, проекция) — цена
  перекладывается на качество диагностик: каждое нарушение объясняется одной
  фразой на предметном языке.
