# NOTE: source pipeline vs multi-source BI

Контекст: сборка демо-отчёта AI-ландшафта (2026-11-09) прошла путь
Epoch CSV → BULK INSERT в SQL Server → dashspec читает views — и оказалась
живой иллюстрацией развилки, которую стоит зафиксировать до того, как она
возникнет как боль.

## Состояние на сегодня

- dashspec — **db-only BI**: источник = view/sql (SQL-пушдаун, iTVF, один
  коннектор на запрос, G⁻¹, типизация через схемы db).
- Файловые источники существуют, но **второго класса**: `Xlsx` (OPENROWSET)
  и `SqlFile` — листовые origins без композиции, без managed views, без
  участия в iTVF.

## Развилка

**A. Ingestion-конвейер (файлы → db → dashspec).** Отдельный слой (`dsc ingest`
или внешний ETL) заводит XLS/CSV/парquet в таблицы БД; dashspec продолжает
читать только db. Плюсы: инварианты сохраняются целиком (пушдаун, iTVF,
типизация, один коннектор); ingestion — решаемая задача вне ядра. Минусы:
появляется второй артефакт и второй путь обновления данных.

**B. Multi-source BI.** Файловые источники становятся первоклассными
(типизация из схемы файла, композиция, трансформации). Плюсы: dashspec без
обязательной БД. Минусы: позиционирование меняется — это уже не db-BI, а
отдельная архитектура: свой движок запросов/пушдауна per-source, свой G⁻¹,
свои коннекторы — существенное расширение ядра, не срез.

## Рабочая позиция (не решение)

- **A — путь по умолчанию**: любой новый формат заводится конвейером в db;
  демо AI-ландшафта — прецедент.
- **B** — отдельно возможная эволюция; если friction конвейера когда-нибудь
  станет постоянной болью — отдельный ADR с оценкой цены, не тихое разрастание.
- Файловые leaf-origins (xlsx/sql-file) сохраняются как есть — escape hatch,
  не направление развития.
