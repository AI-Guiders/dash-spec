# DASHSPEC-NOTE-visual-tree-role-contract

Черновик модели, нарисованный оператором 2026-11-03 в разборе «чья это шкура» (кейс: flatpickr-календарь фильтров, невидимые опции комбобокса на navy). NOTE отвечает на вопрос «существует ли Visual Tree как артефакт» сверкой с каноном; из неё потом собирается ADR-поправка к [ADR-0112] (его Open #5).

## 1. Ответ: дерево существует — это канон, а не новая архитектура

Модель оператора `DashSpec → VisualTree → RenderStack → Web Page` **ложится на принятый канон почти буква в букву**:

| Уровень модели | Канон | Где |
|---|---|---|
| DashSpec | документ + wiring-граф: семантика, намерение | [ADR-0091] |
| **VisualTree** | **`SlotPlane` — собранная слотовая плоскость, SSOT визуальной композиции**; «дерево несёт намерение (что: семьи, слоты, виджеты, тема-токен)» | [ADR-0111] §1, [ADR-0112] Decision |
| RenderStack | «стек решает всё визуальное»: компоненты, CSS, хром, тема своим пониманием слова | [ADR-0112] §1–§2 |
| Web Page | один язык стека-хозяина, гости изолированы в слотах | [ADR-0112] §3 |

Цитата-якорь (оператор, 2026-10-22, [ADR-0112] Context): *«хост даёт дерево, рендер целиком решает, как и что рендерить. В дереве уже есть тип семьи»* — постановка старше этой записки на две недели; NOTE её **проясняет, не придумывает**.

## 2. Артефакт дерева сегодня — из чего собран (фрагменты, не один файл)

1. **`SlotPlane`** ([ADR-0111] §1): собирается один раз на bootstrap (`SlotPlaneBuilder`), несёт структуру — слоты, доски по маршрутам, эффективные раскладки per viewport-класс; «плоскость — структура, а не контейнер сущностей», жильцы — узлы графа документа как есть.
2. **Семейные payload'и** (`CardRenderResult`): `Chart` / `Matrix` / `Table` / `Gantt` / `Number` — семантические данные семьи, ноль визуалии; рендерер стека интерпретирует.
3. **Виджет-роли фильтров**: `widget = combobox | day | chips | range` в спеке (`FilterParser`) — роль названа словом на уровне дерева.

Оператору на полях (2026-11-03): «фрагменты» выше — не про незавершённость. `SlotPlane` собирается **один раз на bootstrap** (`ReportSpecBootstrap` → `SlotPlaneBuilder.Build`) и дальше **неизменна при рендере** — сессия накладывает выбор поверх, плоскость не трогается ([ADR-0111]). «Фрагменты» — про то, что модель оператора «VisualTree» ложится на **три разных артефакта** (плоскость + payload'и семей + виджет-роли фильтров), а не один файл-дерево.

**Один артефакт — уже он.** Возражение оператора (2026-11-03): «система выкатывает стеку всё, что ему нужно — расчёты, размеры, вложенность, кто какие функции несёт → стек выбирает компонент → страница; мы для этого и выносили сборку на компилятор, чтобы рендер не считал». Ответ: так и устроено, и **один артефакт уже есть — сама плоскость**. Со стековой точки зрения это не «три фрагмента», а одно дерево: плоскость несёт структуру и вложенность, жильцы-узлы несут семантику (семья/kind/виджет-роль читаются стеком с жильца). Ноль расчётов раскладки на рендере — инвариант [ADR-0111].

Единственное, что **принципиально не прекомпилируется** — семейные данные: payload'и зависят от значений фильтров рантайма (запрос в БД на каждое изменение), это данные, не раскладка; «рендер не считает» относилось к расчётам структуры, и они вынесены.

Остаётся единственный реальный зазор между «один артефакт» и моделью: функции роли жильца сегодня **выводятся стеком из внутренностей узла** (семья/kind/виджет), а не декларированы на нём явно. Превратить вывод в чтение явного контракта — и есть ADR-поправка (п. ниже).

Дырка против модели оператора одна, но она именно та: **роль не несёт контракта функций** («date-input обязан уметь culture-парсинг») — роль это слово, а реализация у фильтров жёсткая (оба стека рендерят компоненты Filter.Builtins, маппинга роль→реализация на стек нет). Это в точности **Open #5 [ADR-0112]**: «граница filter-плагин vs стек: что несёт плагин (семантика, bind-контракт, тексты) и что стек (компоненты, CSS)».

## 4. Открытые вопросы (сузено после сверки)

1. ~~Существует ли VisualTree~~ — **решено** (§1–2): существует, `SlotPlane` + payload'и + виджет-роли; пробел — не существование, а **контракт функций роли**.
2. **Контракт ролей фильтров** (= Open #5 [ADR-0112], наш кейс): роль `date-input` обязана уметь culture-парсинг — кто это декларирует (плагин) и кто связывает с реализацией (стек). Формулировка контракта → снятие вопроса.
3. **Токены гостей** — закрыто оператором (2026-11-03): гость семьи может знать токены хозяина. Смысл стека — единый CSS стека; CSS меняется по необходимости, гости потребляют его переменные. Нейтральный токен-контракт не нужен (и совпадает с Rejected «общая палитра-контракт» [ADR-0112]). Ссылки ECharts-guest на `--rz-*` — не отклонение, а потребление CSS семьи.
4. **Шкура flatpickr**: по модели — стеку (темы стека красят `.flatpickr-calendar`); плагину остаётся структурный css. Механика — после ADR по п.2.
5. SelfMade-стек: модель покрывает («другой набор компонентов»), миграция стандартная.
