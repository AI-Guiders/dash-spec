# DASHSPEC-ADR-0123: Группировка — runtime-трансформер payload→payload

## Context

Пользовательская фича «группировка таблиц» дважды заваливалась на определениях:

- **Группировка** — строки остаются строками, таблица раскладывает их под
  сворачиваемые заголовки по значению колонки (▼ 1965 → Иванов, Сидоров).
  Ничего не считается и не выбрасывается.
- **Сводка** — «сколько родилось в каждый год»: строки заменяются
  агрегатом по группам.

ADR-0121 дал database-носитель `group_by { by, agg }` — SQL-семантику
(GROUP BY + агрегатная функция), то есть сводку. Попытка выжать из
него группировку со строками — ошибка категории: SQL GROUP BY по
определению схлопывает. Нативный группировочный рендер Radzen требует
POCO-свойств у строк — динамические колонки это не дают без рефлексии
(запрещена линией проекта), и группирует он только загруженную страницу.

Носитель для группировки уже есть: runtime-трансформеры ADR-0078/0120 —
преобразование payload→payload, как `to_zone` (поток не меняется — меняется
представление; рендер остаётся тупым).

## Decision

**Группировка — runtime-трансформер `group_by { by }`; сводка остаётся
database `group_by { by, agg }` без изменений. Одно имя — два носителя,
локальность (контракт узла, ADR-0120) выбирает семантику.**

1. **Runtime-шаг `group_by { by = <column> }`** (без `agg`): батч строк
   упорядочивается по ключу и несёт **групповую организацию** — контекстные
   раны (ключ группы, смещение, длина) поверх тех же строк. Ни одна строка
   не теряется, не создаётся, не агрегируется.
2. **Рендер тупой**: табличный payload несёт раны групп; рендер-плагин
   только отрисовывает их (сворачиваемые заголовки + строки). Никакой
   группировочной логики в слое показа, никакого выбора данных.
3. **SQL-носитель не трогаем**: `group_by { by, agg }` остаётся сводкой —
   и мы не пытаемся получить от database-группировки то, чего SQL не даёт.
   Шаг без `agg` в database не компилируется (loud): сводка требует
   агрегата.
4. **Различие — контракт параметров**: `agg` отсутствует → рантайм
   (группы строк), `agg` задан → database (сводка). Компилятор
   маршрутизирует по этому признаку; путаница исключена на уровне грамматики.
5. **`order_by { by, direction }` — шаг потока, двуносимый по контракту
   локальности (как фильтры):** на database-пути улетает в `ORDER BY`
   запроса, сворачиваясь с остальными database-узлами в один SELECT; на
   runtime — сортирует в памяти (стабильно). Группировка опирается на него:
   `group_by` требует упорядоченности по ключу и сам её обеспечивает, после
   чего раны собираются **одним проходом** по результатам — SQL ORDER BY
   плюс программная сборка, без второго запроса. Шаговой форме порядок
   принадлежит по праву: `order_by` диаграммы — лишь sugar ее проекции.
6. **Интерактив и сахар — вне первого среза** (урок ADR-0120 п.6): сначала
   явный transform-узел в спеке и живой покупатель; кнопки/драг в хедере
   таблицы родятся из кейса.

## Alternatives considered

- **Нативный рендер Radzen (AllowGrouping)** — требует POCO у строк
  (динамические колонки ⇒ только рефлексия/Emit — запрещены) и группирует
  лишь загруженную страницу. Отвергнуто.
- **Группировка в слое показа** (компонент сам строит группы) — размывает
  «рендер только отображает»; организация данных — это преобразование и
  его место в трансформере. Отвергнуто.
- **Расширить database group_by группами-со-строками** — SQL GROUP BY
  схлопывает; получить группы строк из одного SELECT нельзя. Отвергнуто:
  не пытаемся получить от носителя то, чего он не даёт.
- **Временные таблицы (#temp)** — серединный путь «сначала материализуй,
  потом группируй как хочешь»: рабочий в SQL, но добавляет управление
  состоянием СУБД в компиляцию. Отложено до покупателя с реальным объёмом.

## Consequences

- `+` группировка таблиц становится записью в словаре трансформов; рендер
  получает готовую организацию и остаётся тупым (принцип tz).
- `+` одно имя с честной развилкой по контракту: `by` — группы, `by + agg` —
  сводка; грамматика сама предотвращает путаницу.
- `−` батч-модель расширяется групповыми ранами (payload→payload влечёт
  организацию рядом с данными) — механика executor'а чуть сложнее плоских
  шагов.
- `−` группируются строки, дошедшие до рантайма (страница/поток) —
  полный охват больших таблиц требует явного управления TOP, как и везде.
