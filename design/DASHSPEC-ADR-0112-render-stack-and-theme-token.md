## Context

Ветка `feature/radzen-visual` заменяет самописные viz-компоненты на Radzen. Пакеты 1–2 вычистили владение CSS (хаб Surface, rviz-префиксы, App.razor — точка сборки), но живой экран (оператор, 2026-10-22, вкладка «Обзор») показывает, что владение **визуальным языком** всё ещё разорвано:

- бренд-хром хоста (белый) — хостовый слой, ему там место;
- тема отчёта — тёмно-синяя с белым акцентом;
- Radzen — серые карточки, красные кнопки: тема красит всё, что попало в её компоненты — вкладки, кнопки, карточки, — потому что **хром поверхности собран из Radzen-компонентов**, а тема Radzen глобальна и грузится последней (порядок ссылок — переходный договор, `22bcaf3`/`8f9e0c7`).

Три визуальных языка на одном экране — симптом: хром ничей, CSS собирает хост, тема общая. Историческая причина — до появления взрослых фреймворков визуальное размазалось по своим контролам и CSS; Radzen пришёл **поверх**, а не вместо.

Оператор (2026-10-22, постановка): рендер — последний самодостаточный этап; хост даёт дерево, рендер **целиком** решает, как и что рендерить. В дереве уже есть тип семьи (heatmap, bar, chart, …) — значит выбор визуального фреймворка — внутреннее дело рендера.

## Decision

### 1. Рендер-стек — явный уровень поверх семей

**Рендер-стек решает одну простую задачу — каким визуальным образом выразить намерение автора** (оператор, 2026-10-22). Всё в этом ADR — следствия этого определения: дерево/плоскость несёт намерение (что: семьи, слоты, виджеты, тема-токен), стек — визуальное выражение (как: компоненты, CSS, хром, тема своими средствами). Критерий для спорных решений: «это про намерение или про выражение?» — второе принадлежит стеку.

```
Host ──(SlotPlane / дерево, ADR-0111)──▶ Render → (ChooseRender)
      ├─▶ DashSpec-builtin (self-made: matrix-canvas, charts.js, свои parts)
      ├─▶ Radzen (тема + хром + семейства диаграмм)
      └─▶ SomethingElse (ECharts, чистый JS, …)  ──▶ ClientBrowser
```

- Дерево несёт семью; рендер мапит семью на реализацию стека. Маппинг — внутреннее дело рендера, не дерева. Де-факто уже так: matrix → canvas, остальные семьи → Radzen — здесь это становится архитектурой, а не случаем.
- **Стек решает всё визуальное, не только диаграммы** (оператор, 2026-10-22): как рендерить виджеты (фильтр-контролы, календари, чипы, переключатели) и прочие контролы поверхности — тоже решает стек. Дерево/плоскость несёт **семантику** (что за виджет, bind-контракт [ADR-0009], какая семья, какой слот), стек — **как это выглядит**: Radzen-стек рендерит фильтры своими компонентами, builtin — своими. Развитие [ADR-0060]: filter-плагин регистрирует виджет-семью и её семантику; визуальная реализация — маппинг стека (граница «плагин vs стек» — Open).
- **Маршрутизация семей — внутри стека** (оператор, 2026-10-23): автор спеки не указывает рендер диаграммы — стек решает, чем выражать каждую семью, и может делегировать семью/kind другому рендеру-гостю (Radzen-стек: «heatmap — не моя, рендерит builtin»). Per-diagram `render` в спеке умирает как авторская опция; редкие исключения живут в маппинге стека.
- **Спеки, дерево, хост не меняются при добавлении стека.** «Захотим чистый JS — добавим чистый JS (привет ECharts), никакой завязки» (оператор). Новый стек — новый рендер-плагин ([ADR-0059] вертикален: компоненты + CSS + тексты).

### 2. Тема — семантический токен, не палитра (оператор, 2026-10-22)

Нет «нашего и не нашего» CSS: **CSS задаётся тем, что используется для рендера**. Автор задаёт тему словом — `light`, `dark`, … — и каждый стек имеет **своё** понимание этих слов: Radzen — свой dark, ECharts — свой theme-объект, builtin — свои токены. Передали `dark` — стек сказал «ага, у меня dark — вот это» и применил.

- **Единство смысла, не единство пикселей.** Соседство стеков на одной странице допустимо: каждый красит своим пониманием слова, никто не тянет глобальную палитру.
- **Текущий тёмно-синий — это тема** (оператор: «наш тёмно-синий это просто тема, наша тема»): первый житель словаря, дефолт builtin-стека — не «артефакт самописности» и не стандарт для чужих стеков.
- **Темы — плагины** (оператор, 2026-10-22): словарь тем — не зашитый список, а **реестр, пополняемый theme-плагинами** — как семьи ([ADR-0059]), фильтры ([ADR-0060]), типы ([ADR-0081]): плагины умеют расширять язык и добавлять сущности ([ADR-0033]). Тема-плагин регистрирует имя темы и её реализации в стеках, которые он знает; базовой набор (light/dark) несут сами стеки или builtin. Тема без реализации в выбранном стеке — дефолт стека + громкий warning, не молчаливая ерунда.
- Механизм: тема едет в спеке/дереве токеном → Surface передаёт выбранному стеку → стек применяет своими средствами. Токены темы в CSS-хабе Surface как «общая тема» умирают.

### 3. Стек-хозяин и гости

- **Хозяин поверхности** — стек, которому принадлежит хром (вкладки, кнопки, карточки-рамки). Его тема красит хром; серость/цветность хрома — скин стека, настраиваемый его средствами, не конфликт.
- **Правило одного хозяина на поверхность.**
- **Гость** (второй стек на той же странице, например matrix-canvas рядом с Radzen) рендерит только внутри слота, без глобальных стилей. rviz-префиксы и изоляция matrix-canvas (пакет 1 ветки) — уже это правило, задним числом.
- Бренд-хром хоста — вне механизма тем: хостовый shell ([ADR-0111] §2, борда host-модуля).

### 4. Точка сборки CSS уезжает из хоста

App.razor перестаёт перечислять CSS плагинов и тему Radzen: рендер-стек сам подключает свои ассеты (Blazor HeadOutlet / стили сборок). Хост снова тонкий: дерево + монтирование. Порядок ссылок «тема последней» — переходное состояние, умирает вместе с переездом точки сборки.

### 5. Хром поверхности принадлежит стеку

RadzenTabs, кнопки, карточки — компоненты стека-хозяина; смена стека меняет хром вместе с диаграммами. Surface.Blazor худеет до: монтирование + выбор стека + общие контракты слотов ([ADR-0111] — вход).

### 6. Выбор стека: блок `host` и ds-слои (дополнение, 2026-10-23)

**Блочная грамматика уже умеет всё нужное** (оператор, 2026-10-23): планетарные настройки — блок `host` в ds. Ключи блока — однотокенные имена блочной грамматики (`render`, `color_scheme` — уже устоявшиеся имена); формы с пробелами из раннего черновика (`render stack`, `render theme`) были иллюстрацией слоёв, не грамматикой. Реализовано 2026-10-23 (переходно): блок парсится, bootstrap складывает его поверх легаси-блоков `configuration`/`presentation` по ключам.

```text
module host dashspec_host

host
  language = "ru-RU"
  color_scheme = dark
  render = selfmade
  provider_default = "sqlserver"
end host
```

`plugins load` остаётся в томл-бандле переходно: DLL-активация планетарная (см. ниже), переезд списка — отдельный заход вместе со сносом томла.

- **Парсер ds — в ядре хоста, не в плагинах**: порядок запуска работает — ядро парсит host.ds → читает блок `host` → догружает названные сборки. Никакого toml-механизма для этого не нужно.
- **host.ds — единственный host-модуль** (ADR-0111 §2). DashSpec — сама планета (конституция федерации): дефолт планеты — embedded `host.ds` в сборке хоста; внешний host.ds — оверрайд **развёртывания** (конкретной установки), не «другой планеты». Имя `.dashhost` (ADR-0054) — исторический дубль, умирает; ADR-0054 — к ревизии.
- **Слои — все ds, один тип** (Combinations `FieldOverlay`, ordered fold):

```text
1. embedded host.ds — дефолт планеты DashSpec (блок host: shell, stack, theme, language, plugins)
2. host.ds развёртывания (опц.) — оверрайд конкретной установки
3. спека отчёта — render stack / theme / defaults.culture
4. внутри стека — маппинг семья/kind → рендер (делегаты гостям: Radzen-стек отдаёт heatmap builtin'у); per-diagram render в спеке умирает — автор рендер не выбирает (оператор, 2026-10-23)
```

- **Plugins-активация — только планетарный слой**: отчёт не решает, какие DLL грузить, — это не его намерение.
- **Томль умирает**: `[host]` / `[presentation]` / `[plugins]` / `[viz]` — всё уезжает в блок `host`; `[presentation]` уже приговорён (`HostBootstrapTomlGuard` → «presentation block in .dashhost»), культура отчёта уже в ds (ADR-0090 `defaults.culture`). Временно остаётся один toml-ключ — путь к host.ds — до конвенции «host.ds рядом с хостом».
- **Секреты — никогда в ds**: строки подключения, ключи — env/отдельные хранилища; в ds — имена провайдеров.

### 7. Монтирование ассетов — решено (2026-10-23)

Стеки и плагины монтируют свои ассеты компонентами в позиции вызова (`SelfMadeStackHead/Scripts`, `RadzenStackHead/Scripts`, `*BuiltinsHead`, `RadzenVizHead`) — без HeadOutlet. Хост линкует только собственные скрипты. Порядок каскада — переходное смешанное состояние (§4), физически сохранён.

## Rejected

- **«Подогнать Radzen под нашу палитру»** (кастомизация темы Radzen под тёмно-синий как цель) — нет «нашего» стандарта палитры; есть словарь тем, каждый стек понимает его по-своему (оператор, 2026-10-22).
- **Общая палитра-контракт между стеками** (единые цветовые токены как контракт) — единство пикселей не цель; при желании близости — работа внутри стеков, не в контракте.
- **Хост как точка сборки CSS** (текущее App.razor) — сворачивается (§4).

## Приёмка

- На одном экране — один визуальный язык стека-хозяина (хром + карточки + диаграммы); гости изолированы внутри слотов.
- Смена theme-токена меняет вид через маппинг стека; тема вне словаря — дефолт + warning.
- Добавление нового стека (ECharts) — только новый рендер-плагин; ноль изменений в хосте, спеках, дереве.

## Open

1. Форма theme-плагина: что несёт (имя + описание vs per-stack реализации) и где живёт базовый набор (в стеках vs builtin-плагин тем); грамматика объявления темы в спеке.
2. Куда едет theme-токен: поле документа/спеки или атрибут плоскости ([ADR-0111] SlotPlane) — решить при первом прохождении.
3. Механика подключения ассетов стеком в Blazor (HeadOutlet vs изоляция сборок) — спайк в рамках ветки.
4. ~~Маппинг семей на стеки: per-family vs per-surface~~ — решено (2026-10-23): per-surface — стек выбирается `presentation.render` (host-модуль → спека); маршрутизация семей — внутри стека, с делегатами гостям; автор рендер не выбирает.
5. Граница «filter-плагин vs стек» для виджетов ([ADR-0060]): что несёт плагин (семантика, bind-контракт, тексты) и что стек (компоненты, CSS); допустимы ли per-stack переопределения в плагине; дефолт стека для неизвестной виджет-семьи.
